# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

construct3-chef mutates Construct 3 projects, which store their data as JSON files on disk (`eventSheets/`, `layouts/`, `objectTypes/`, `scripts/`). It exposes the same library two ways: a yargs **CLI** (`src/cli.ts`) and an **MCP server** (`src/mcp/server.ts`). Both are thin wrappers over the pure library in `src/c3/`. When adding a capability, implement it in `src/c3/`, then surface it in both `cli.ts` and `server.ts`. **Known exception — `src/c3/search.ts` is MCP-only** (`server.ts`'s `search` tool + the `src/index.ts` barrel; the CLI never imports it). The CLI's similarly-named `search-dsl` is a *separate, narrower* implementation rooted at `extractedDir`, and `search-docs` is a different capability again (`aceLookup.ts`). Don't infer the surface from the name: this cost real time on [#159](https://github.com/GenvidTechnologies/construct3-chef/issues/159), which was filed `area:cli` with acceptance criteria written as a `search --type json` CLI invocation that does not exist. Check the imports before labelling or scoping work against a `src/c3/` module. Keep the **result rendering** in the `src/c3/` library too (a shared formatter both surfaces call), so the CLI and MCP outputs stay byte-identical instead of drifting — e.g. `aceLookup.ts`'s `formatLookupResult` is rendered once and consumed by the `search-docs` CLI subcommand and MCP tool alike. The **addon read surface** follows the same shape: `src/c3/addonReader.ts` (off-barrel) is the shared `.c3addon` reader — hybrid extracted-dir→zip via `fflate`, exposing the `readAddonEntry` primitive — behind the `read-addon` CLI subcommand + MCP tool, with `formatAddonInfo`/`formatAddonList` rendered once; sibling addon tools (#109–#111, #98) import `readAddonEntry` rather than re-unzipping (see ADR `wiki/decisions/0008`). The first sibling, `src/c3/addonValidator.ts` (also off-barrel; #107, extended by #108), backs the read-only `validate-addons` CLI subcommand + MCP tool: it consumes `discoverAddons`/`readAddonMetadata` to report bundled-`.c3addon` ↔ `project.c3proj.usedAddons` metadata mismatches, package-integrity failures, and orphan/missing/duplicate package-consistency findings, rendering once through the shared `formatAddonValidation`. `validate-addons` was then extended (#98, folded into the existing command rather than shipping the `validate-addon` command the issue originally proposed — see ADR `wiki/decisions/0009`) to also cross-check each addon's `aces.json`/editor-`plugin.js` `properties` against every `lang/*.json` locale it ships: `src/c3/addonLangValidator.ts` (off-barrel) runs the per-locale check (gated on lang-file presence, so lang-less addons are unaffected), sourcing ACE param ids via `addonReader.ts`'s `listAddonEntries`/`readAddonEntry` and property ids via `src/c3/addonPropertyExtractor.ts` (off-barrel; a best-effort string-literal scan of `plugin.js`, since properties are JS-declared, not JSON). A new `--addon <id|path>` CLI option / `addon` MCP param (resolved by `addonDiscovery.ts`'s `resolveAddonTarget`, either a discovered addon id or a path to a raw addon source tree) scopes a run to one addon, enabling use against addon-dev repos as well as C3 projects. Two `validate-addons` **false positives** surfaced by the canonical-fixture editor-import (#130) were later corrected (#132): effect addons are **exempt from the `aces.json` required-entry check** in `checkIntegrity` (`kind !== "effect"` — effects ship no ACEs; `addon.json` stays required for all, `aces.json` for plugin/behavior only), and `checkMetadataMismatch` **dropped the `name` field** (a package's `addon.json` display name legitimately differs from `usedAddons[].name`, the user-assigned *instance* name), keeping `id`/`author`/`version` — the `id` row is the identity anchor. (`validate-addons` has **no severity concept** — every finding is CI-failing via `cli.ts` — so the fix was to *drop* the wrong check, not downgrade it. #132 item 1, the in-tree fixture's incomplete effect application, was deferred to #130.) The `addon-validate` fixture's `build-archive.mjs` was generalized to **kind-route** archives into `addons/{plugin,effect,behavior}/` and zip each source's actual file set (was plugin-only + a fixed three-file set), preserving byte-identity of the existing packages. The read-side sibling `src/c3/addonInventory.ts` (off-barrel; #111, capability 7) backs the read-only `list-addons` CLI subcommand + MCP tool: `listAddons` reconciles bundled `.c3addon` packages (flat `discoverAddons`), `project.c3proj.usedAddons`, and editor-only addons (`bundled:false`) into one row per addon id — classified bundled/editor-only/missing/orphan — rendered once via `formatAddonInventory` (it presents the same reconciliation `validate-addons` reports as findings, but as a never-failing inventory; duplicate/nested-package detection stays a `validate-addons` concern). Its prep step extracted the previously-private `readUsedAddons`/`UsedAddonEntry` into a shared off-barrel `src/c3/addonManifest.ts` and promoted `resolveAddonId` onto `addonReader.ts`, both now shared by `addonValidator` and `addonInventory`. The next sibling, `src/c3/addonAceDiff.ts` (off-barrel; #109, capability 4), backs the read-only `diff-addon-aces` CLI subcommand + MCP tool: `diffAddonAces` diffs two `AceEntry[]` lists by `(kind, id)` identity, reporting added/removed ACEs and, for ACEs present on both sides, changed ordered `{name,type}` param signatures, rendered once via `formatAceDiff`; `resolveAceSource` sources each side via `addonReader.ts`'s `readAddonAces`, from a local `.c3addon` file path (**deliberately not** containment-guarded to `--project-dir`, unlike its read-addon/validate-addons siblings — the tool exists to diff packages living outside the project, e.g. a freshly downloaded release archive), a discovered addon id, or an extracted addon dir. It's **local-only in v1**: a remote source (a GitHub release tag/URL, fetched on the fly) is deferred to a follow-up issue — download both `.c3addon` files first and diff locally in the meantime. The latest sibling, `src/c3/addonAceUsage.ts` (off-barrel; #110, capability 5), backs the read-only `scan-addon-usage` CLI subcommand + MCP tool: `scanAddonUsage` reports a plugin addon's **presence** (object types/families whose `plugin-id` matches, enumerated via the new shared off-barrel `src/c3/projectObjects.ts` `readProjectObjects`/`ObjectDefn` seam) and its event-sheet **ACE call sites** (conditions/actions matched on `(kind, id)` — never `objectClass`, the caller-supplied addon name — via c3source `visitEvents`), with an optional `--from` **blast-radius** mode that runs `diffAddonAces` inline and flags call sites hitting a changed/removed ACE, deliberately widening the match set to `current ∪ removed` so dangling calls to a removed ACE (the stale-reimport fallout the tool exists to catch) are still surfaced; rendered once via `formatAddonUsage` (see ADR `wiki/decisions/0010`). Its MCP tool includes the `txId` footer (it reads `eventSheets`/`objectTypes`/`families`, all tx-tracked — like `list-addons`, unlike `diff-addon-aces`), and its CLI exits 1 in blast mode only when affected call sites exist (an opt-in CI gate). `scan-addon-usage` shipped **plugins-only** (#110), then was extended to **behavior** addons (#124, ADR `wiki/decisions/0011`): a `UsageMatcher` seam in `addonAceUsage.ts` isolates plugin-vs-behavior presence/match/attribution behind a shared event-walk + `formatAddonUsage` (ADR 0011 predicted the extension point #125 would reuse this seam for effects too). Behavior presence is keyed on `objectTypes`/`families` `behaviorTypes[]` `behaviorId` (**not** `plugin-id`); `ObjectDefn` gained an additive `behaviors: BehaviorRef[]{behaviorId,name}` (P1). The load-bearing subtlety: a call on a family **member** carries the member's own `objectClass` (not the family's) with `behaviorType` = the instance name, and is attributed to the **family** presence row while the call site keeps its real `objectClass` — a naive `objectClass ∈ hosts` predicate silently drops it. #124 also required the shared reader to **strip a UTF-8 BOM** (`addonReader.ts`): real C3-exported `.c3addon` `aces.json`/`addon.json` ship a BOM that `JSON.parse` rejects, silently emptying the ACE set for **every** addon tool — the synthetic build-archive fixtures never had one, so it stayed latent until the real behavior fixture. Discovery widened to `addons/behavior` (fixing a latent `addonLangValidator` section-key misfile). Built-in behaviors (Timer/Persist) remain unscannable by id (no bundled package → no ACE set). `scan-addon-usage` was then extended to **effect** addons (#125, ADR `wiki/decisions/0012`) — a course-correction from ADR 0011's prediction: effects have no ACEs and no event-sheet nodes, and their application sites (layers/layouts) aren't `ObjectDefn`s, so the `UsageMatcher` seam structurally can't fit; effect support ships instead as a dedicated `scanEffectUsage` path that bypasses the event-walk shell entirely, sharing only the result types and `formatAddonUsage` rendering. Presence IS usage for an effect: the four application sites are an object type's/family's own `effectTypes[]` entry (an additive `ObjectDefn.effectTypes: EffectRef[]`) and a layout's/layer's `effectTypes[]` entry (a new `readLayoutEffects` reader in `projectObjects.ts`, since layers/layouts have no `ObjectDefn`); per-instance `effects{}` overrides are out of scope, subsumed by object-type presence. `--from` blast radius is redefined for effects — no ACE param signature to diff, so every application site is exposed by a version bump (`blast.affectedCount = effectSites.length`), and the CLI's exit-1-in-blast-mode gate fires whenever the effect is applied anywhere. `scan-addon-usage` was finally extended to **expression usage** (#123, ADR `wiki/decisions/0015`) — the last #100 child, **closing #100**. Expressions aren't structured `(kind,id)` nodes; they live as text inside condition/action parameter strings, so a new `collectExpressionSites` pass in the event walk tokenizes every string param (c3source 1.8.0 `extractExpressionReferences`, adopted via #136) and resolves each `Object.expr`/`Object.Behavior.expr` token to an expression ACE `id` via a new `UsageMatcher.matchExpression` seam method (`findExpression` over the `readAddonAcesModel` seam). Surfaced as a parallel `expressionSites` collection + a distinct `PresenceRow.expressionSiteCount` (NOT folded into `callSiteCount`) — the `matchExpression`-on-the-seam vs separate-path call is the inverse of the #125 effect decision (expressions ride the event walk, so the seam fits; effects don't). `--from` blast flags CHANGED/REMOVED expression refs and **widens the resolution model with the diff's removed expressions** so a dangling ref to a removed expression still surfaces (the expression analogue of the removed-key match-set widening). Capability 8 then shipped as `sync-addon-metadata` (#145) — renamed from the originally-proposed `sync-addon-version` because `author` is in scope alongside `version` — via a new off-barrel `src/c3/addonMetadataSync.ts` behind a CLI subcommand and a dual MCP-tool pair (`READ_ONLY` `preview-addon-metadata-sync`, `MUTATE` `sync-addon-metadata`): the addon cluster's **first mutation** — every prior addon tool is `READ_ONLY`. A mandatory, no-default `--direction` (`manifest-from-package` | `package-from-manifest`) names which side is source of truth — direction is a human decision the tool never infers, since C3's four-part dotted addon versions aren't semver — and only `manifest-from-package` writes; `package-from-manifest` is always a read-only report, because chef has no `.c3addon` writer. The write parses `project.c3proj` **by identity** (c3source's `readProjectManifestTolerant`), field-assigns `version`/`author` in place, and serializes via `writeProjectManifest`/`serializeProjectManifest` — never a spread, which would reorder keys and drop unmodeled fields — the same byte-fidelity discipline `projectSync.ts` already follows for its own write to the same file. See ADR `wiki/decisions/0017`. The deferred remote-source follow-up for `diff-addon-aces` is the remaining gap.

## Commands

This repo uses **npm** (committed `package-lock.json`). It's published to npmjs.com as `@genvidtech/construct3-chef` via the `GenvidTechnologies/public-github-actions` GitHub Actions recipe (`.github/workflows/`; formerly `genvid-holdings/genvid-public-ci`); the gate runs `npm ci`. (`@genvidtech/construct3-chef` is the current scope — the package was renamed from `@genvid/construct3-chef` to the GenvidTechnologies org scope and republished starting at `0.11.2`; the old `@genvid/construct3-chef` scope is frozen/deprecated at `0.11.1`. This mirrors the `@genvid/*`→`@genvidtech/*` transfers of the leaf deps `c3source`/`mcp-utils` below.)

```bash
npm install                             # install deps (fetches @genvid/* from npm)
npm test                                # mocha + tsx + chai, all test/**/*.test.ts
npm test -- --grep "foo"                # run tests matching a name (npm needs `--` before forwarded args)
npm run test:file -- test/c3/sidUtils.test.ts   # run a SINGLE file (test:file has no glob, so the path narrows)
npm run lint                            # eslint over src/ AND test/, --max-warnings 0
npm run typecheck                       # tsc --noEmit — checks src/ ONLY (test/ has known type errors; see commit 0b4c515)
npm run build                           # tsc → dist/, then prepends a node shebang to dist/cli.js
```

> **Single-file runs need `test:file`, not `npm test -- <path>`.** The `test` script hardcodes the `'test/**/*.test.ts'` spec glob, and mocha **merges** (doesn't override) a positional path with a config/inline spec — so `npm test -- test/c3/foo.test.ts` silently runs the *whole* suite (the path just dedups against the glob). `test:file` is the same command minus the glob, so the forwarded path is the only spec. `--grep` works on `npm test` because it's a name filter, not a spec.

There is no dev script for the CLI. Run it in-place with `npx tsx src/cli.ts <subcommand> --project-dir <path>` — tsx compiles the `.ts` on the fly, so no build is needed. The package's `main`/`types`/`exports` point at the built `dist/` (what published consumers import); the `construct3-chef` bin also only exists after `npm run build` (it points at `dist/cli.js`).

> **Probing an internal `src/c3/` function ad-hoc** (not the CLI): write a temp `.mts` file at the repo root and run `npx tsx that-file.mts` (delete it after). Do **not** use `npx tsx -e "<import … from './src/…'; …>"` — the inline-eval form with multi-line ESM imports silently yields no output in this repo's `NodeNext`/`"type":"module"` setup, so it's not usable for quick probes.
>
> **The repo root is only for probes that import `src/`.** A probe that needs no repo import — a `node:fs` behavior check, a question about a dependency's actual semantics — belongs in the **scratchpad**, not the tree, so it can't be committed by accident and needs no cleanup step to remember. Three traps in getting one to run there: the Bash tool's `$TMPDIR` is **unset** on this machine (a `> "$TMPDIR/probe.mjs"` heredoc writes to `/probe.mjs` → `Permission denied`), so use the session scratchpad's absolute path; **`/tmp` is not a shared location either, and this one fails silently across tools** — the Bash tool resolves `/tmp` to `C:\Users\FABIEN~1\AppData\Local\Temp`, while a *Windows* `node`/`npx` process resolves the same string to `C:\tmp`, so a file written by a bash redirect (`… > /tmp/x.txt`, which succeeds) and read back by `node -e 'readFileSync("/tmp/x.txt")'` fails `ENOENT` on a path that looks entirely plausible in the error message; the same absolute-scratchpad-path rule fixes it, but the `$TMPDIR` reasoning above does **not** cover it — a reader who knows only that `$TMPDIR` is unset may reasonably conclude `/tmp` is the safe substitute, which is exactly the trap; and the scratchpad has **no `node_modules`**, so a bare `import { walkFiles } from "@genvidtech/mcp-utils"` fails `ERR_MODULE_NOT_FOUND` — import the installed copy by absolute path instead (`import { … } from "file:///C:/repos/construct3-chef/node_modules/@genvidtech/mcp-utils/dist/walkFiles.js"`). Reach for this whenever a plan or an issue turns on *"what does this primitive actually do?"*: #160's proposed fix cited `walkFiles` as precedent for a predicate it doesn't implement, and a ten-line scratchpad probe settled it in one run where reading the issue would have shipped a new defect.

### Releasing

Cutting a release is a tag push, not a manual `npm publish`:

1. Bump `package.json` `version` on a topic branch (`npm version X.Y.Z --no-git-tag-version`) and commit.
2. PR → squash-merge to `main`.
3. Tag the **merged** commit: `git tag vX.Y.Z` (annotated is fine) → `git push origin vX.Y.Z`.
4. **After the publish run succeeds, request the downstream pin bump.** This package's MCP server is made for the `gvt-construct3` plugin, which pins an *exact* version (`@genvidtech/construct3-chef@X.Y.Z` as an `npx` arg in its `plugin/.claude-plugin/plugin.json` `mcpServers`) — so a release does nothing for plugin consumers until that pin moves. File an issue on [`GenvidTechnologies/claude-code-plugin-gvt-construct3`](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-construct3/issues) asking to bump the pin to the new version, **including a summary of the release's changes** (e.g. `git log <prev-tag>..<new-tag> --pretty='- %s'`) and a note to re-run their `docs/tool-surface-reconciliation.md` step if the MCP tool surface changed. See [gvt-construct3#8](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-construct3/issues/8) for the template.

The `v*.*.*` tag triggers `.github/workflows/publish.yml`: the gate job runs `npm ci` + lint/typecheck/test/build/`publish --dry-run`, then the publish job runs `npm publish --provenance --access public` via OIDC trusted publishing (no stored npm token). **The publish job fails the "Verify tag matches package version" step if the tag minus its `v` ≠ `package.json` version** — so always tag the commit that already carries the bump (don't tag `main` before the bump merges). (Cautionary precedent: `0.2.0` was merged to `main` but never tagged, so it was never published — the tag push, not the merge, is what publishes.)

**Fixture materialization.** `test/fixtures/construct3-chef-sample/` is not fully tracked in-tree — it's materialized from the `GenvidTechnologies/construct3-sample` git submodule (`test/fixtures/construct3-sample/`, pinned by gitlink; currently `v0.7.0`). `scripts/prep-fixture.mjs` (`npm run fixture:prep`) self-inits the submodule — `git submodule update --init`, **load-bearing, not redundant**: the shared `public-github-actions/node-gate.yml` gate checks out no submodules by default — then `fs.cpSync`s **two** submodule trees into the fixture dir — its `project/` tree over the root, and its `archive-sources/` tree to `<fixture>/archive-sources/`; it's wired as the `pretest`/`pretest:file` npm hook, so `npm test` / `npm run test:file` materialize it automatically, locally and in CI. Root `.gitignore` ignores the fixture dir wholesale except the **12-file `extracted/` golden read-surface**, re-included by negation — chef tracks only its own rendering, nothing that's canonical-fixture material. `prep-fixture.mjs` is copy-only (never deletes), so stale copies survive indefinitely — leftovers from *earlier* pins, not just files a bump removes — which is why the update protocol below opens with an **unconditional** `git clean -fdX` purge rather than a conditional one. `archive-sources/` **must** land inside the fixture root rather than be referenced in the submodule: `resolveAddonTarget` containment-guards an extracted-addon-dir path with `resolveWithin(projectRoot, …)`, so a `--from` pointing outside the root is rejected — keeping the path at `<fixture>/archive-sources/<id>` is what lets the `scan-addon-usage` blast-radius tests address it unchanged. (#139 moved `archive-sources/` + the addon builder upstream into `construct3-sample`, ending the copy-drift risk of chef keeping its own copy; the canonical repo now also gates every shipped `.c3addon` against its sources.) See ADR `wiki/decisions/0013` for the consumption design (chef as prototype/superset consumer; `construct3-sample`'s own ADR 0001 owns the canonical submodule-mechanism rationale).

**Golden test.** `test/c3/sampleProjectGolden.test.ts` regenerates `extracted/` from the materialized fixture `test/fixtures/construct3-chef-sample/` and diffs it against the committed golden (`…/extracted/`), guarding the generate→`extracted/` pipeline (esp. layout-summary `fullLayerName`/global composition + DSL coordinates). **It does *not* validate that the source fixture loads in C3** — it only diffs the read surface. c3source's parser is lenient (it types e.g. variable `comment` / group `description` as optional), but the C3 editor *requires* them as strings on load. So when hand-authoring fixture event JSON, mirror what `eventSheetMutator.buildVariable`/`buildGroup` emit (or a real export) and verify by importing into C3 — green tests alone are **not** sufficient, though the automated guard now backstops hand-authored fixtures: `test/c3/fixtureLoadValidity.test.ts` runs every fixture event sheet through `validateForEditor` and asserts zero issues, catching a `variable`/`group` missing the required string field at test time (closes #61). (Hit on #58: a fixture variable + group missing `comment`/`description` passed the whole suite but failed C3 load with `expected string`. **Established habit:** when a hand-authored *or* generated fixture fails C3 load, contribute the editor-required field rule to the upstream `EDITOR_FIELD_RULES` table in c3source#33, which shipped as `validateForEditor` in c3source 1.4.0.) The fixture is a real C3 export that deliberately exercises the awkward cases: nested objectType subfolders (`global`/`images`/`tiles`) mirroring the manifest tree, a family, a Sprite with a nested animation subfolder, a Tilemap/TiledBackground with a `tilemapBrushes/` tree, `.ts` scripts, a global layer defined in each of two layouts and overridden by the other (`"global layer"` sourced from Second Layout, `"previously local"` from Main Layout — the first real-data pair sourcing from *different* layouts), `function-block`s both with and without a `functionDescription` (`MyAsyncFunction` is `async` with two parameters; `MyFunction` has neither), a `custom-ace-block` (`NavButton.OnClickAction`) holding a `callFunction` action with a **positional `parameters` array** plus a parameter string carrying expression text (`Functions.CallMapped("mymap", "MyFunction") + Functions.MyFunction`), and a boolean event variable read by a `compare-boolean-eventvar` condition. What it does **not** carry is any `uistate/` directory or `*.uistate.json` file — C3 writes them, but the canonical export excludes them (`construct3-sample`'s own `project/.gitignore`), so the generators' editor-local filtering (`isEditorLocalPath` applied over path segments in `generateSidRegistry`) is exercised only by synthetic temp-dir tests and never by this fixture; a uistate regression test written against the sample fixture passes **vacuously** (a trap `test/mcp/serverHandlers.test.ts` fell into and stayed in until [#149](https://github.com/GenvidTechnologies/construct3-chef/issues/149) closed it, replacing the two vacuous assertions with the seeded synthetic `list-event-sheets`/`list-layouts` dimension tests — see ADR `wiki/decisions/0019`). Object types are flat `<Name>.json` in named subfolders, **not** per-type directories. The custom effect `MyCompany_MyEffect` is applied at three sites — Sprite2 (objectType), TextFamily (family), and Second Layout's layer 1 — via a real editor-authored application (the canonical export was round-tripped through C3 r49500), which **fixed** the earlier incomplete hand-authored application (`effectTypes[]` referenced the effect without the `usedAddons` entry / per-instance `effects` data a real application writes, so the **project** null-pointered on import; #132 item 1, closed by adopting the canonical fixture in #130 — items 2–3, two `validate-addons` false positives, are separate and stay tracked in #132). The three-site application is a **change**, not just a completion, from the retired hand-authored four-site data (which named the effect `"My custom effect"` and included a layout-stack site plus a nested sublayer 1.1.1); the effect-scanner tests were re-baselined to the real editor values, with recursive `subLayers` walk coverage preserved via a synthetic temp-dir test. When a generator change *intentionally* alters output, regenerate the golden (materialize the fixture first if you haven't run the test suite recently):
```bash
npm run fixture:prep
npx tsx src/cli.ts generate --project-dir test/fixtures/construct3-chef-sample
```

**Update protocol (bumping the canonical pin).** **Step 0, unconditional:** `git clean -fdX -- test/fixtures/construct3-chef-sample/` → `npm run fixture:prep` → `npm run fixture:verify`, *before* the gitlink moves, so the red state that follows is attributable to the new canonical bytes alone. This is **not** conditional on the bump removing a canonical file: because prep is copy-only, leftovers from earlier pins persist indefinitely — the `v0.3.0`→`v0.7.0` bump found 14 pre-#130 `*.uistate.json` files the canonical repo has never tracked at any tag. `npm run fixture:verify` (`scripts/verify-fixture-parity.mjs`) is the oracle: no `*.uistate.json`, no `uistate/` dirs, exactly 12 tracked overlay files, and a recursive path-set + byte compare of the submodule's `project/` tree against the materialized fixture. (The clean can't eat the golden — `.gitignore` ignores the fixture dir with `/*`, not `/**`, so the `!…/extracted/` negation un-ignores that whole subtree.) Then: bump the submodule gitlink (`cd test/fixtures/construct3-sample && git checkout vX.Y.Z`, commit the gitlink change) → `npm run fixture:prep` → `npm run fixture:verify` again at the new pin (an `only in fixture` path means the bump *removed* a canonical file — clean and re-prep; `only in submodule` or a byte mismatch means prep itself is broken) → regenerate the golden (above) → run the full automated gate (`fixtureLoadValidity`'s `validateForEditor`, `typecheck`, the golden byte-diff) → **manually import the regenerated project into the C3 editor** — the automated gates check event sheets and the read-surface diff, not a whole-project editor load (the #132/#130 precedent: a null-pointering project passed every automated gate) → **then clean + prep + verify AGAIN, because the import itself dirties the fixture**: opening the project makes C3 write editor-local state into it (`*.uistate.json` at several levels plus a `layouts/uistate/` directory), which `git status` can't show and copy-only prep never removes. Re-run `npm run fixture:verify` after the import and expect it to FAIL with `only in fixture` — that is the editor's leftovers, not a defect, and it is almost certainly how the 14 pre-#130 files accumulated. A clean import shows **only** `only in fixture`; a `byte mismatch` or `only in submodule` would mean the editor rewrote canonical bytes, which is a real finding → re-classify any canonical file additions/removals against the 12-file overlay list (a canonical path colliding with an overlay path needs a rename, not a silent overwrite).

## Leaf dependencies

`@genvidtech/c3source` and `@genvidtech/mcp-utils` are public packages on npm; `npm install` fetches them from the registry like any other dependency. Versions are pinned in `package.json`. (`@genvidtech/c3source` is the current scope — the package was transferred from `@genvid/c3source` to the GenvidTechnologies org and republished starting at `^1.6.0`; the old `@genvid/c3source` scope is frozen/deprecated at 1.5.0. `@genvidtech/mcp-utils` is likewise the current scope — the package was transferred from `@genvid/mcp-utils` to the GenvidTechnologies org and republished at `^0.5.1` (API-identical to the now-frozen `@genvid/mcp-utils@0.5.0`; closes #104). These packages were once private tarballs pulled from Azure Blob via a `download-deps` + 1Password bootstrap; that machinery was retired when the packages went public — `git log` for the history.)

> **Checking for a new upstream release:** use `npm view <pkg> version --prefer-online` (or check the package's GitHub tags). Plain `npm view` and the editor's "new version available" banner both read a *cached* registry index and lag fresh publishes — don't conclude you're current off the cached read when deciding whether to adopt.

- **`@genvidtech/c3source`** — the C3 JSON domain layer: type definitions (`EventSheet`, `Condition`, `Layout`, …), file discovery (`find_all_eventsheets_path`), and primitives like `extractScriptsFromSheet`, `formatCondition`. Treat it as the source of truth for C3's on-disk schema.
- **`@genvidtech/mcp-utils`** — MCP plumbing: `ReadWriteLock`, `ExpectedChanges`, `paginateText`, `exposeDocs`, `Logger`.

**Adoption posture (the recurring "should this live upstream?" call).** Push **traversal, numbering, and discovery** into c3source — that's domain logic (`visitEvents`/`visitLayers`, the `isCountingEvent` event counter, the `find_all_*_path` finders). Keep **rendering/presentation** local — the `extracted/` read-surface (DSL text, index, layout summaries) is *this tool's* invention, not C3 on-disk schema, so it must not move upstream even when a c3source helper could shave a few lines. The split was settled in #27 (the DSL formatter drives traversal via `visitEvents` but renders locally) and guides the remaining adoption issues (#25/#26/#28). When a needed traversal/discovery primitive is missing upstream (e.g. #28 wanted a `.dsl.txt` file finder that c3source doesn't export), file an intent request on `GenvidTechnologies/c3source` rather than re-rolling it here. **Owning the *fact* upstream isn't sufficient — check the primitive's *shape* fits the consuming *operation*.** **⚠️ After adopting an upstream *behavior* change, revert-confirm the local guards that overlap it — a green suite post-bump does not mean your guards still guard.** When upstream starts doing what a local clause was doing, the local clause's tests can keep passing **for a different reason**, silently converting a guarded clause into an unguarded one with no diff, no failing test, and no actor to notice. This is distinct from the "does the bump change our output?" question the per-version entries in `wiki/process/leaf-dependency-ledger.md` answer: nothing about the *product* changed, only what the *test* was proving. **So: for each local guard the upstream change overlaps, delete it and confirm a test still fails; if none does, the coverage is now vacuous and the guard needs a test written at the surface upstream does *not* reach.** Related: a `^0.x.y` range **excludes** the next minor (`^0.5.1` = `>=0.5.1 <0.6.0-0`), so a 0.x bump is real dependency work, not the adoption-without-a-bump shape the c3source entries in `wiki/process/leaf-dependency-ledger.md` describe. Both rules above are stated here without their cases: the #42 / c3source#21 shape-fit precedent (also ADR [`0006`](./wiki/decisions/0006-upstream-ownership-boundary-and-adoption-posture.md), which names it the canonical "request the right shape, wait" precedent) and the #168 / mcp-utils 0.6.0 revert-confirm case both live in `wiki/process/leaf-dependency-ledger.md` under their version entries.

The same posture governs **`@genvidtech/mcp-utils`**: generic MCP/config *plumbing* goes upstream, the project-specific schema and behavior stay local. **The version-by-version record — what each upstream release shipped, what chef adopted, and the deliberate declines that must not be re-litigated — lives in [`wiki/process/leaf-dependency-ledger.md`](./wiki/process/leaf-dependency-ledger.md), one section per package, oldest entry first.** Routing test for a new version fact: if it would need editing when the next version ships, it belongs in the ledger; if it survives every version, it belongs here. Before adopting a new upstream release, read that package's newest ledger entry — the declines are recorded there rather than silently skipped, and the newest entry names what to check at the next bump.

## Module system gotchas

ESM throughout (`"type": "module"`, `NodeNext`). **Relative imports must use the `.js` extension even though the files are `.ts`** (e.g. `import { foo } from "./generators.js"`). `strict` is on. Two tsconfigs: `tsconfig.json` (src-only, emits to `dist/`, used by build + typecheck) and `tsconfig.test.json` (adds `test/`, `noEmit` — exists for editors, not wired into the `typecheck` script).

**Public-API surface = the `src/index.ts` barrel.** It re-exports each module wholesale (`export * from "./c3/dslFormatter.js"`, …), so *every exported symbol* a module declares becomes published API the moment it ships in `dist/`. Deleting or renaming an exported function/type/interface is therefore **semver-breaking** even when nothing inside the repo still imports it (e.g. #27 removed the unused-internally `formatEvent`/`EventCounter` — breaking for any consumer importing them from `@genvidtech/construct3-chef`). Since `1.0.0` this is no longer a cheap change: a removal or rename requires a **major** bump, so prefer deprecating a symbol (keep it re-exported, document the replacement) over deleting it, and note any unavoidable removal in the commit body plus at the release tag (see [Releasing](#releasing)). (Pre-`1.0.0` such removals were absorbed by a minor — e.g. #27's `formatEvent`/`EventCounter`, and the `readDiskDirNames`/`syncNameFolder` removals.) To keep a symbol internal, don't re-export its module from `src/index.ts`.

## The two-surface data model

This is the central idea. There are two views of the project — plus a third artifact that is neither, described at the end of this section:

- **Source JSON** (`eventSheets/`, `layouts/`, `objectTypes/`) — the write surface. The actual C3 project. Never hand-edit blindly; mutate via recipes.
- **`extracted/`** (DSL `.dsl.txt`, index `.dsl.idx.txt`, TypeScript `.ts`, layout summaries, `template-scope.txt`, `sid-registry.txt`) — the read surface. Human/AI-readable, regenerated from source by the 6 generators in `src/c3/generators.ts`. Committed alongside source for diffing. The directory name defaults to `extracted/` but is configurable via `extractedDir` in an optional `construct3-chef.config.json` at the project root (loaded by `src/c3/chefConfig.ts`'s `loadChefConfig` over mcp-utils' `loadProjectConfig`; the value is path-contained to the project root). The same config file also carries `navigation` (nav convention overrides) and `ops` (`ops.dir` / `ops.watch` for user-defined ops). The source-JSON dir names are C3-fixed and stay hardcoded. See `wiki/reference/cli.md` § Configuration file and `wiki/reference/ops.md`.

**The third artifact: a pack-time `docs/`, which exists only inside the published tarball.** It is neither surface above — not source, not the read surface — and it is **gitignored, never committed, and absent from a dev checkout**. `scripts/gen-docs-alias.mjs` generates it from `wiki/` during `prepack` and `postpack` deletes it again, exactly the way `dist/` already works. It exists because mcp-utils' `exposeDocs` resolves a **hardcoded, flat, non-recursive** `<packageDir>/docs`, which the `docs/` → `wiki/` consolidation (ADR 0028) silently emptied; the alias rebuilds the flat surface `exposeDocs` expects. See ADR [`0029`](./wiki/decisions/0029-flat-docs-alias-generated-into-the-tarball.md), which also records its **deletion condition** — this whole mechanism is retired once [mcp-utils#15](https://github.com/GenvidTechnologies/mcp-utils/issues/15) ships a configurable directory, a recursive scan, and a non-`undefined` `list` callback. ⚠️ **This does not contradict the standing "never fix the conventions audit by recreating `docs/`" rule** — that rule is about a *tracked* `docs/` documentation tier, which stays retired. Nothing here is hand-authored and nothing is committed; the served set is a rule (every tracked `wiki/**/*.md` whose basename does not match `gen-wiki-index.mjs`'s `RESERVED`, plus a generated `docs/index.md` manifest), and `node scripts/gen-docs-alias.mjs --check` is its exact-match oracle. **Consequence for development:** the MCP docs resource is **empty when running from source** and populated only from an installed package — run `npm run docs:alias` to inspect it locally, and assert against `npm pack` output rather than the working tree, which is why `test/mcp/docsResource.test.ts` packs and extracts rather than reading from disk. ⚠️ **Anything wired into `prepack` must write its diagnostics to `stderr`, never `stdout`** — `npm pack --json` merges the script's stdout into its own output, so a single `console.log` renders the manifest unparseable and silently breaks every consumer of it, including this repo's own pack assertions. That defect is invisible until the script actually runs under `prepack`; a standalone run looks fine.

> **Adding a generator touches ~9 sites in lockstep.** `GENERATORS` in `src/c3/generators.ts` is now the single source of truth (#178, ADR `wiki/decisions/0022`): `cli.ts`'s `runGenerators` filters it directly by `--only`, and `server.ts`'s `GENERATOR_STEPS` is `.map()`-derived from it, so the old private `GENERATOR_NAMES` + `generators` array in `cli.ts` no longer exist as separate drift sites and `GENERATOR_STEPS` itself no longer needs manual editing. The rest are a hardcoded count that still silently drifts if missed: the four `totalSteps`/`progressTotal` constants in `server.ts` (the `runGenerators` default and the apply-recipe / clone-layout / workflow tool handlers — each is "N + generators", so all bump by one) and the `regenerate` tool's description string; the golden test's `before` hook (`test/c3/sampleProjectGolden.test.ts`); `EXPECTED_TRACKED_FILES` in `scripts/verify-fixture-parity.mjs` (a new generator adds a golden file, so the tracked-overlay count moves); plus `wiki/reference/generators.md` / `wiki/reference/cli.md` / `wiki/index.md` / `wiki/architecture/mcp-architecture.md` and the count in this file. Grep `totalSteps`/`progressTotal` in `server.ts` after wiring a new one. `test/c3/generatorOutDir.test.ts` is deliberately NOT one of these sites — it iterates `GENERATORS`, so a seventh entry gets outDir-self-sufficiency coverage automatically with no edit to that file. `README.md`'s MCP `regenerate` row is likewise NOT one, for the same mechanical reason but only since [#199](https://github.com/GenvidTechnologies/construct3-chef/issues/199) — and it is worth knowing *why* it was exempted, because it earned its place the hard way: that row is a generator-count site (it reads "Run all N generators") which this enumeration never named, and it had drifted to **5** against six, unnoticed, precisely because nothing listed it. `test/readmeCommandInventory.test.ts` now asserts the row's count against `GENERATORS.length` instead, so the count is derived rather than restated — the same fix the "name the items, let the count fall out" rule in § "Conventions" prescribes for prose, applied to a doc by a test. The lesson generalizes past this row: a site absent from a lockstep list is not thereby safe, it is merely unwatched, so when a count in prose turns out to have drifted, check whether the enumeration that should have caught it names that site at all. (Cf. the objectType lockstep note below.)

Workflow loop: **read `extracted/` to locate a target → write a recipe targeting it by SID → apply to source JSON → regenerate `extracted/` → sync `project.c3proj`.** After any source mutation, `extracted/` is stale until regenerated.

### SIDs are the addressing system

C3 nodes carry a stable `sid` (a random integer in `[1e14, 1e15)`). Recipes target nodes by SID (`"in": "sid:123…"`) rather than fragile JSON paths — you discover SIDs from the `.dsl.idx.txt` index or via the `resolve-anchor` MCP tool. `src/c3/sidUtils.ts` holds a **module-level SID context** that must be initialized (`initSidContext` from `sid-registry.txt`, or `initSidContextFromSet`) before any SID is generated, and reset after. `recipeApplier.applyParsed` wraps the whole apply in `initSidContext`/`resetSidContext` so every newly generated SID is globally unique against the registry. Tests that touch SID generation must init the context themselves.

## Recipe pipeline

- **`recipeInterpreter.ts`** — declares the `Recipe` type (`objectTypes`, `addInstVars`, `files`, `layouts`), all the op shorthands, `validateRecipe`, and the **pure** execution functions (`executeRecipe`, `executeFileOps`, `applyReplacements`) that transform in-memory `EventSheet` objects with no I/O.
- **`recipeApplier.ts`** — the orchestrator with I/O. `applyRecipeInner` applies in a fixed order: **objectTypes → addInstVars → layouts → files**, then writes files and regenerates. Adding an objectType touches three places in lockstep: the `objectTypes/*.json`, `scripts/ts-defs/instanceTypes.d.ts`, and `scripts/ts-defs/objects.d.ts`. Layout ops dispatch into `layoutMutator.ts`.
  - **Two validation chokepoints guard every event-sheet write** (both fire in `validate-recipe` dry-run *and* `apply-recipe`, before any disk write): (1) `assertEditorValid` (c3source `validateForEditor`) — **editor-load** validity, the per-sheet check that the C3 editor will accept the project on import (#84); (2) `validateInsertedCustomActions` (`customAceIndex.ts`, off the barrel) — **runtime-resolution** validity, project-context-aware, rejecting a recipe-inserted family-provided custom-action that lacks `customActionObjectClass` (#88). These are *different layers*: a runtime-resolution defect passes editor validation and renders **byte-identical DSL** (`formatAction` never reads `customActionObjectClass`), so it's invisible until C3 runtime — hence the dedicated check. `customAceIndex` enumerates custom-action *definitions* from `custom-ace-block` events (via c3source `extractFunctions`, which carries the owning `objectClass`) + `families/*.json` membership.
- **`workflowExpansion.ts`** — composite **workflow ops** (`extract-template`, `templatize-in-place`, `clone-replica-to-layouts`, `replace-instance-with-replica`) expand into primitive layout ops in a pre-pass before the layout-file loop runs, fanning out across multiple layout keys when needed. Dispatch and dry-run logging iterate the expanded `Map`, so workflows are validated as their primitive sequence.
- **`eventSheetMutator.ts`** — low-level builders (`buildBlock`, `buildAction`, …) and tree edits (`insertEvent`, `resolveNode`, SID-index building) over a single sheet.

> **`SidIndexEntry.indexInParent` is a snapshot, not a live index.** `buildSidIndex` records each node's position once; the `parentArray` reference stays valid but the stored index goes stale the moment an earlier op in the same recipe batch splices that array. Any op that positions relative to a resolved node (insert-after, remove, move) must recompute with `parentArray.indexOf(node)` — never trust `indexInParent` for placement. (This was gotcha #34: the `insert-event` `after: "sid:X"` branch used the stale snapshot and misplaced/appended.)

The recipe reference (all event-sheet + layout ops, SID addressing, builder shorthands) lives in `wiki/reference/recipe-reference.md`; generator internals in `wiki/reference/generators.md`.

## MCP server state model (`src/mcp/server.ts`)

The CLI is stateless; the server adds a concurrency layer worth understanding before editing it:

- **`PROJECT_ROOT` / `PROJECT`** — the module-level project root (a string) and a co-located `C3Project` handle (`openProject(PROJECT_ROOT)`), both finalized in `startServer` before any tool runs. `startServer` resolves `PROJECT_ROOT` via mcp-utils `resolveRootFolder` (precedence `--project-dir` > `C3_PROJECT_DIR` > `project.c3proj` discovery > cwd) *before* `loadChefConfig`, then sets `PROJECT = openProject(PROJECT_ROOT)`. Handler bodies derive C3 source-subfolder paths from `PROJECT` (`PROJECT.eventSheetsDir`, `PROJECT.findAllLayouts()`, …) rather than re-joining literals — so any code that reassigns `PROJECT_ROOT` (the test seams `__setProjectRoot`/`__resetTestState`) **must reassign `PROJECT` too**, or it goes stale. (Single-root only; multi-root is #95. See ADR `wiki/decisions/0007`.)
- **`txId`** — the `OptimisticWatcher`'s monotonic counter (`watcher.txId`, incremented via `watcher.bump()`) — bumped on every source-file mutation. Optimistic concurrency: read tools / `validate-recipe` return the current `txId`; `apply-recipe` / `sync-project` accept an expected `txId` and reject if it has moved.
- **`extractedDirty`** — true when source has changed since the last regenerate; read tools append a stale warning and `checkSourceFreshness` flips it by comparing mtimes. Stays module-level (project-specific); set from the watcher's `onSourceChange` callback.
- **File watchers** — `createSourceWatcher` (`src/mcp/sourceWatcher.ts`) wires @genvidtech/mcp-utils' `OptimisticWatcher` over the source dirs + `project.c3proj`. External source edits bump `txId` and set `extractedDirty` (via `onSourceChange`); `project.c3proj` edits bump `txId` only; an external edit to an **editor-local** path (`isEditorLocalPath` — a `uistate/`/`ts-defs/` dir, a `*.uistate.json` basename, exact `tsconfig.json`) bumps neither. That third case is filtered at the **watcher factory**, not inside `onExternalChange` — `OptimisticWatcher.handleEvent` bumps `txId` unconditionally before invoking the callback, so a callback-side filter can suppress `extractedDirty` but not the bump. See ADR `wiki/decisions/0018`. Self-induced writes are masked by wrapping them in `watcher.suppress(async () => { … })` (synchronous suppress window) plus `watcher.expect(absPath)` for paths whose watcher event may land after the window closes — when editing a mutate tool, wrap its writes in `suppress` (and `expect()` anything written outside that call) or the watcher will spuriously mark state dirty.
- **`ReadWriteLock`** serializes writes, allows concurrent reads. Tools are tagged `READ_ONLY` / `REGENERATE` / `MUTATE` annotations.
- `CancelledError` paths still bump `txId` (`watcher.bump()`) and set `extractedDirty` because source was already written before regeneration was interrupted.

## Conventions

- C3 JSON is written tab-indented with **no trailing newline** — the file ends at its closing `}`/`]`, matching what the C3 editor itself writes (all 27 files in the pinned canonical fixture end this way). Source writes (`eventSheets/`, `layouts/`, `objectTypes/`) go through the shared, deliberately off-barrel `src/c3/sourceJson.ts`'s `writeSourceJson(filePath, value)` so the invariant lives in one place instead of being re-derived at each call site. `project.c3proj` goes through c3source's `writeProjectManifest`/`serializeProjectManifest`, which already emitted no trailing newline — this makes the two consistent rather than changing the manifest. `extracted/` remains the one exception: it's chef's own read surface, not C3 source, and keeps its trailing newline (still byte-diffed by the golden test). This **reverses** the previously-documented two-form rule, where event-sheet/layout writes used to append `+ "\n"`; see ADR `wiki/decisions/0030` and #195.
- Prettier: 120 cols, spaces for `.ts`, **tabs** for `.json`. ESLint extends prettier and disables `no-unused-vars` / `no-explicit-any`.
- **Formatting IS gated by `npm run lint`** (as of #54). `lint` runs ESLint *and then* `npm run format:check` (`prettier --check "src/**/*.ts" "test/**/*.ts"`), so Prettier conformance is enforced wherever lint runs (incl. the shared `public-github-actions` gate). ESLint itself still extends `eslint-config-prettier`, which only *disables* ESLint's formatting rules — it never runs Prettier — so the `format:check` step is what actually enforces it. The whole repo conforms; run `npm run format` (`prettier --write`) to fix drift before committing. **`test/fixtures/` is `.prettierignore`'d wholesale** — it's real C3-export data (the SDK runtime/plugin `*.d.ts`, fixture scripts) plus the generated `extracted/` read-surface the golden test diffs byte-for-byte; never reformat it. (Pre-#54 history: `projectSync.ts` was whole-file tab-indented and ~21 files had drifted because formatting was ungated; #54 conformed them in one isolated `style:` commit and wired the gate.)
- All file I/O is rooted at a `--project-dir` (defaults to cwd); paths inside recipes/tools are relative to that root. Mutate tools include path-traversal guards — keep them.
- **Editor-local path classification goes through `src/c3/editorLocal.ts`** (off-barrel: `hasEditorLocalSegment` / `isEditorLocalPathUnder`), never a hand-written predicate — re-deriving one dimension of a three-dimension rule is precisely the mistake #146 made and ADR [`0016`](./wiki/decisions/0016-shared-file-walk-adoption-triage.md) corrected ("reachability is not classification"). It applies c3source's `isEditorLocalPath` over path **segments**, which is what covers a `uistate/`/`ts-defs/` *directory* as well as a `Foo.uistate.json` *sibling file* and an exact `tsconfig.json`. Consumed by `generateSidRegistry`, the MCP source watcher (`sourceWatcher.ts`), and `server.ts`'s sid-registry freshness scan; `customAceIndex.ts`'s families walk ([#152](https://github.com/GenvidTechnologies/construct3-chef/issues/152)) and `spriteScaffold.ts`'s objectTypes walk ([#149](https://github.com/GenvidTechnologies/construct3-chef/issues/149)) are now migrated too — the former onto `C3Project.findAllFamilies()` with a contextual rethrow (it owns a `C3Project` handle and can afford to fail loudly on an I/O fault), the latter kept on `walkFiles` + `isEditorLocalPathUnder` (its contract is a bare directory and its callers are barrel-exported at 1.0.0, so they depend on the missing-dir → `[]` degrade `find_all_objectTypes_path` doesn't offer). **Selection rule:** reach for the c3source named collector (`project.findAll*()` / `find_all_*_path`) when the site owns a project root/`C3Project` handle and can afford to fail loudly on an I/O fault; reach for `walkFiles` + `editorLocal.isEditorLocalPathUnder` when the site's contract is a bare directory, is barrel-exported, or depends on the missing-directory/`ENOENT` degrade — never hand-write the editor-local predicate either way. Deliberate declines, recorded rather than silently skipped: `generators.findJsonFiles` (ADR 0016 §3) and `projectSync.readDiskDir` (§2) and `discoverAndPlanImageCopies` (`images/` isn't project source). `search.ts`'s `json`-type walk closes the last un-migrated project-source walk ([#159](https://github.com/GenvidTechnologies/construct3-chef/issues/159)): its four `walkFiles` sites and two single-file branches (which bypass `walkFiles` entirely) all filter via one predicate anchored at `baseRoot` — the *base* the walk is rooted from, not the *walked directory* — because a caller-supplied walked dir can itself be the editor-local directory (e.g. `path: "layouts/uistate"`), leaving nothing to classify if relativized against itself. ⚠️ Coverage must be **synthetic temp-dir** — the canonical fixture tracks zero editor-local files at every tag, so a fixture-based assertion passes vacuously. See ADR [`0018`](./wiki/decisions/0018-editor-local-writes-are-not-source-changes.md), ADR [`0019`](./wiki/decisions/0019-two-walk-primitives-one-classification-rule.md), and ADR [`0020`](./wiki/decisions/0020-search-walk-editor-local-anchor.md).
- **A retired plugin/scope name lives in more places than `/gvt-dev:audit-conventions` scans.** Its retired-token check reads the docs root + `CLAUDE.md` + `<wikiDir>/`, minus `excludePaths` (gvt-dev ADR-0041; before 4.19.0 it was `docs/**.md` + `CLAUDE.md` only, which since the consolidation had resolved to `CLAUDE.md` and nothing else here — see § "Where to read more") — so it still structurally cannot see **user-facing strings in `src/`** — and those are the higher-stakes ones, since they ship to consumers of the published package: `aceLookup.ts`'s `formatLookupResult` no-cache note (rendered into CLI *and* MCP output) and the `search-docs` MCP tool `description` in `server.ts` both name a sibling plugin. It also skips any line containing an `http` URL, which hides in-scope hits in link-dense prose (gvt-dev [#232](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-dev/issues/232); scope widening is [#233](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-dev/issues/233)). So **grep the whole repo, don't trust the audit's count** — the `genvid-c3`→`gvt-construct3` sweep found 8 sites where the audit reported 6. Before editing a rendered string, check the tests that assert on it (the three `no c3-reference cache` asserts match only the stable prefix — luck, not design). Deliberately excluded: `wiki/decisions/` (an ADR is a historical record) and "formerly …" provenance prose (`genvid-holdings`/`genvid-public-ci`). ⚠️ That exclusion covers a retired token in **prose**, NOT a **link target** — [#203](https://github.com/GenvidTechnologies/construct3-chef/issues/203) found 20 links pointing through the retired `genvid-holdings` org, five of them inside `wiki/decisions/`, and all 20 were repointed: a pointer exists to resolve, and fixing where a citation points changes nothing the record asserts, whereas rewriting `formerly …` prose would make the sentence false. See ADR [`0032`](./wiki/decisions/0032-retired-org-link-targets-are-repointed-prose-is-not.md). `test/retiredOrgLinks.test.ts` now guards the class, matching the **URL form** rather than the bare token — which is exactly what keeps its exclusion list empty, since the two `genvid-holdings` mentions on this very line are prose and carry no `github.com/` prefix. It is the complement of the audit's scanner, which skips every line containing `http`; note the audit missed this class for a **second** independent reason the issue did not name — its default deny-list (`genvid:`, `genvid-dev:`, `genvid-c3`) never contained `genvid-holdings` at all, so the upstream fix alone would not have caught it. This recurs — `@genvid/*`→`@genvidtech/*`, `genvid-c3`→`gvt-construct3`, `genvid-dev:`→`gvt-dev:`, `.genvid-agent.json`→`.gvt-agent.json`.
- **A guard test that was never red must be proven by *mutation*, not by reversion.** The revert-confirm rule in § "Leaf dependencies" ("delete the local guard and confirm a test still fails") answers *"does this row depend on the fix?"* — which is unanswerable for a row that was **green from the start**, the case a behaviour-preserving refactor produces by construction. Ask the other question instead: *can this row fail at all?* Force the system into the state the row forbids and confirm it goes red. Precedent both ways: [#177](https://github.com/GenvidTechnologies/construct3-chef/issues/177)'s R9 stayed green through a full red→green ritual while passing identically **in the exact state it claimed to forbid**, and [#154](https://github.com/GenvidTechnologies/construct3-chef/issues/154)'s R6 mutation (append `"\n"` to the `project.c3proj` write) correctly went 47 passing / 1 failing. ⚠️ **Confirm the mutation actually landed before reading the run** — a mutation that silently no-ops returns **green**, which reads as "the row is vacuous" and sends you to rewrite a test that was fine; grep the mutated expression, then run. ⚠️ **The mutation must target the PRODUCTION code the row guards, never the test itself** — *"delete an assertion and confirm it goes red"* is a plausible-sounding inversion that cannot work, since removing an assertion makes a row weaker rather than failing. [#183](https://github.com/GenvidTechnologies/construct3-chef/issues/183)'s T16 was specified that way by the designer and had to be re-derived as a rendering mutation (`!`→`?` in `reportStrayFiles`), which correctly took 12 rows red — including all eight it claimed to protect. ⚠️ And a **third** vacuity shape that *neither* rule catches, because the row genuinely is red overall: one half of a **paired** assertion passing **for the wrong reason**. #183's T1 asserted `exitCode === 1` for a not-yet-registered CLI flag, and that half **passed** at the committed-red commit — yargs `.strict()` rejects an unknown argument and also exits 1 — so only the paired stdout assertion was ever really red. An exit-code assertion about an unimplemented flag is therefore not evidence on its own; pair it with an assertion on output that only the real feature can produce, and read *which half* went red rather than trusting the row's verdict. ⚠️ **And the mirror of all of them: a check that reports *red* is a hypothesis too.** Every rule above hardens against a check that passes when it shouldn't; none covers one that **fails** when it shouldn't — and that direction is the more expensive one, because a false red sends you to "fix" an artifact that was already correct, which is how a verified-clean artifact acquires a real defect. Both false reds on [#172](https://github.com/GenvidTechnologies/construct3-chef/issues/172) were bugs in the *verifier*, never the artifact: one split the source spans at the anchor strings used to locate entries, but those anchors sit **mid-entry**, so its chunks straddled entry boundaries and could never be contiguous once headings were interleaved — 10 false failures against a byte-exact move; the other extracted an entry body by slicing to the next `###` and so swept up the intervening `## <package>` heading, failing by exactly that heading's length. Neither was distinguishable from a genuine failure by its output alone. So **diagnose a red verifier before acting on it** — binary-search the longest matching prefix and print both sides at the divergence, which names the discrepancy in one run. Note what a positive control does and does not buy here: it proves the verifier *can* fail, not that *this* failure belongs to the artifact. See ADR [`0024`](./wiki/decisions/0024-project-c3proj-shared-serializer.md).
- **A citation *duplicated across documents* is name-based; `file:line` is for a single in-code pointer.** Cite a test or function by its `describe`/`it`/symbol name (`the `list-layouts` editor-local dimension tests`) rather than `foo.test.ts:281-292` whenever the same reference appears in more than one place — prose in `CLAUDE.md`, an issue body, and a code comment all drift independently, and nothing detects it. A `file:line` in a JSDoc *next to the thing it names* is fine and stays: it moves with its neighbour, and this file is dense with them by design. The rule is about **duplication**, not line numbers per se. Evidence: the one line-numbered cross-doc citation this repo ever carried (`serverHandlers.test.ts`) drifted into **three mutually inconsistent values** across the issue, this file, and `includeTree.test.ts` — while every other citation here, already name-based, stayed correct. Fixing a drifted citation by re-anchoring it to fresh line numbers just resets the clock; convert it instead. **A `§N` section reference into an ADR is governed by the same principle in a weaker form:** `§N` is acceptable — an ADR's sections are numbered in the heading text itself (`### 3. DECLINE — …`), so renumbering is a *visible* edit rather than silent drift — but a **bare** `(§N)` is not, because a reader cannot tell a correct section number from a wrong one without opening the ADR. Name what the section decided alongside the number, or pair each number with the symbol that heading is named after. Evidence: this repo's five citations of ADR 0016's `findJsonFiles` decline were correct at the four that glossed what the section decided (`wiki/decisions/0018`, `wiki/decisions/0019`, `generators.ts`, `spriteScaffold.ts`) and wrong at the fifth — the bullet above — which used a bare section number to cover two declines at once and so silently attributed the `readDiskDir` decline to the `findJsonFiles` section ([#169](https://github.com/GenvidTechnologies/construct3-chef/issues/169)); the failure mode is **opacity, not drift**. When naming an ADR's declines, name them rather than counting them: ADR 0016 has **three** (§2, §3, §4), and a count restated in prose is one more thing to drift. See ADR [`0019`](./wiki/decisions/0019-two-walk-primitives-one-classification-rule.md).
- **`CLAUDE.md`'s own long-form sections are single *unwrapped physical lines*, not wrapped prose** — the "What this is" opener is one such line (12,181 chars as of [#164](https://github.com/GenvidTechnologies/construct3-chef/issues/164)), and re-derive rather than trust that figure: the companion figure this bullet used to quote for the leaf-dependency ledger was stale within two issues, and that ledger's version narrative has since moved out to `wiki/process/leaf-dependency-ledger.md` ([#172](https://github.com/GenvidTechnologies/construct3-chef/issues/172)). Append in place; never reflow one, split it into paragraphs, or let an "add a paragraph" instinct open a new line inside it. The trap is that three line-oriented tools quietly mislead here, which cost real time on #164: `grep -c` counts *lines matched*, not occurrences, so it returns `1` for an entry containing a dozen hits and is worthless as a completeness check (use `grep -o … | wc -l`); `git diff --stat` reports `1 insertion(+), 1 deletion(-)` for a multi-thousand-character append, so it cannot tell an append from a whole-line rewrite — establish that separately (`newLine.startsWith(oldLine)`); and a `file:line` citation into one of these lines addresses ~3k tokens of prose rather than a claim, which is a second reason the name-based-citation rule above is not optional here. Verify an edit's structure with `awk 'NR>=X && NR<=Y {printf "L%d [%d chars]\n", NR, length($0)}' CLAUDE.md`: the line *count* must be unchanged, and only the target line's char count may grow. ⚠️ `grep -o … | wc -l` fixes the *counting* trap but not a **second** one it can't see: a rule bullet that quotes the defective form as its worked example becomes a false positive in every later sweep for that form. **This very bullet is the live instance** — it names `ADR 0016 §3` and `(§2)` just above to illustrate the rule, so a whole-file count of either returns **2** while only L124's is a real citation ([#169](https://github.com/GenvidTechnologies/construct3-chef/issues/169)). Scope such a check to the line (`awk 'NR==X'`) rather than the file, and expect the same shape wherever a convention here is illustrated by the thing it forbids — the retired-token sweeps have it too. A **fourth** tool trap, this one on *size*: `wc -c` counts **bytes** and `wc -m` counts **characters**, and this file is dense enough in multi-byte glyphs (`§`, `—`, `⚠️`) that the two differ by ~500 — so a size quoted in one unit and compared against a figure measured in the other invents a delta that isn't there (posted wrong on [#172](https://github.com/GenvidTechnologies/construct3-chef/issues/172) before being caught). State the unit, and use whichever one the figure you're comparing against used; `awk length($0)` counts characters, matching the per-line figures quoted throughout this bullet. A **fifth** trap, and the only one here that isn't about a tool: a count restated in prose encodes an invisible *convention* for what counts as one item, and **the convention drifts even when the value doesn't**. L87's generator-lockstep count moved `~10`→`~9` in [#178](https://github.com/GenvidTechnologies/construct3-chef/issues/178), correctly — but a reviewer re-counting that same enumeration with the four `totalSteps`/`progressTotal` constants expanded individually got **11** and reported a discrepancy; under *that* convention the pre-#178 figure would have been ~14, not ~10. Neither count is wrong, nothing in the line says which convention produced it, and the failure mode is the reverse of drift: a good-faith recount manufactures a false finding and invites someone to "correct" a number that was right. So when a count survives in prose, either name the convention inline (here: the four progress constants are one site, each doc is its own) or drop the number for the name-them-don't-count form the ADR-declines rule above already prefers — and when reviewing one, derive the reviewer's convention before believing the delta. ⚠️ **And the mirror of that, which is worse because the audit trail argues against you: a corrected count can decay back to its original wrong value by a different route.** The fifth trap above is the convention drifting while the value holds; this is the *value* returning while the convention holds. [#198](https://github.com/GenvidTechnologies/construct3-chef/issues/198)'s served-page count went **41 → 40 → 41**: the design derived 41 without accounting for `RESERVED` also excluding `log.md` (defective), it was corrected to 40 against a 45-page corpus, and then committing ADR 0029 grew the corpus to 46 and took it back to 41 (decayed) — the same number as the original mistake, reached by entirely different reasoning. Nothing looks wrong at the end state, and the recorded correction makes the figure read as *more* trustworthy than an uncorrected one. Note the self-reference that caused it: **a record that states a count of the corpus it belongs to invalidates itself the moment it is committed**, so an ADR or wiki page quoting a page count is always off by its own existence. The remedy is the one the seventh trap already prefers — state the **rule** and let the count fall out, keep any quoted figure explicitly as-of, and assert a `≥` threshold with a generated oracle (`gen-docs-alias.mjs --check`) rather than an equality that a new page falsifies. A **sixth** trap, back on tooling and reaching beyond this file to any *doc-anchored* check: **markdown emphasis inside a phrase defeats a plain-text grep anchor.** `grep -c "does not affect the exit code" wiki/reference/cli.md` returns **0** while the phrase is present three times, because the real text is `does **not** affect the exit code` — the bold sits *inside* the span. The dangerous failure is the quiet one, not the noisy one: you grep for a sentence, get 0, conclude it isn't there, and ship a doc that contradicts the code. It bites hardest on a **survival** row (*"this count must stay 1"*), which reads 0 identically before and after and is therefore unfalsifiable in both directions — the vacuous-guard shape again, arriving through a grep rather than a test. This repo's acceptance rows are routinely doc-anchored greps, so: anchor on a **markup-free span**, and confirm the anchor matches something *today* before trusting the count it returns ([#183](https://github.com/GenvidTechnologies/construct3-chef/issues/183)). A **seventh** trap, the fifth one's authoring-side inverse: that one is about *re-counting* a number someone else wrote, this is about **handing a count to whoever writes the prose**. A count in a brief is not a fact the author verifies — it is a **slot with a known arity**, and an author who cannot find that many items will invent the balance. On [#172](https://github.com/GenvidTechnologies/construct3-chef/issues/172) a dispatch brief said "the four `record before 'fixing' them` declines"; **two** sites carry that exact phrase, and the ADR that came back duly named four items — `generators.findJsonFiles`, `projectSync.readDiskDir`, `SID_SOURCE_DIRS`, and the `descend` note — of which one sits at such a site, the rest being ADR 0016's declines lifted from a different version's entry. Nothing was wrong with the underlying source; the *number* created the shape and the names were fitted to it. A wrong fact invites a check, a wrong arity invites completion — so **name the items and let the count fall out**, in a brief exactly as in the prose the fifth trap governs. And when a fabricated count is corrected, sweep for its copies before believing it gone: this one had also been restated in a `wiki/index.md` entry description, which survived the fix to the ADR body and surfaced only because an unrelated row's count came out wrong. An **eighth** trap, and it is the self-example trap above — the one whose live instance is this bullet's own `ADR 0016 §3` citation and whose remedy is `awk 'NR==X'` — reappearing outside this file, in `src/`: **a comment naming a symbol's *absence* is an exact match for that symbol**, so `grep -c` over source systematically **overcounts call sites** wherever the codebase documents where something is deliberately *not* used. Both are mention-counted-as-use; what changes is that a *source* mention has no single line to scope to. (Distinguish the **sixth** trap, markup defeating a plain-text anchor, which runs the opposite direction — a real instance that fails to match. And this is not the substring false-positive a trailing `(` already guards: the token genuinely appears in call form.) Evidence ([#191](https://github.com/GenvidTechnologies/construct3-chef/issues/191)): `grep -c "\.expect(" src/mcp/server.ts` returns **4** against **2** real call sites, because `server.ts` carries two comments reading *"No `watcher.expect()` needed"* — one of which exists precisely to explain why that site is safe without it. So the `awk 'NR==X'` remedy does **not** transfer; anchor the pattern to a call position (`^\s*watcher\.expect(`) or read `grep -n` output instead of trusting `grep -c`. The compounding danger is that **running a grep feels like verification** — it converts *"I should check this"* into *"I checked this"*, which is how this count reached a dispatch brief under the **verified** label, got faithfully rendered into `wiki/process/leaf-dependency-ledger.md` by a tech-writer that had no reason to doubt it, and passed lint, typecheck, and 1570 tests, since nothing examines doc prose. The gap being crossed is between *"the token appears N times"* and *"there are N call sites"*, and only the second is ever the claim — which is the seventh trap's **name the items and let the count fall out** arriving by a different route, and the reason this bullet's own remedy is a named pair of handlers rather than the number two.

## Commit Format

Conventional Commits: `<type>: <subject>`, where `type` is one of `feat`, `fix`, `chore`, `docs`, `refactor`, `test`. Subject is imperative, lowercase, no trailing period. Body (optional) explains the *why* and any non-obvious *what*, wrapped at ~72 cols. When a commit is authored with Claude Code, end the message with a `Co-Authored-By` trailer:

```
Co-Authored-By: Claude <model> (1M context) <noreply@anthropic.com>
```

**`<model>` is the model that actually authored the commit** — read it off the running session (e.g. `Opus 5`), don't copy the example. This line is an attribution record, so a pinned version here is wrong the moment the model changes, and pinning has already gone stale twice: the trailer read `Opus 4.6` for nine commits, was hand-bumped to `Opus 4.8 (1M context)` in `93b4627`, and was still claiming 4.8 while Opus 5 was authoring. Drop the ` (1M context)` qualifier if the session isn't a long-context one.

Squash-merged PRs carry a `(#N)` suffix on the subject (added by the merge), e.g. `feat: composite template workflow ops + MCP tools (#9)`.

## Pull Request Format

Host is **GitHub** (`gh` CLI). PR title follows the same Conventional Commit shape as the squash subject. The body should summarize what changed and why, call out verification done (lint/typecheck/test), and note any follow-ups. When generated with Claude Code, append the `🤖 Generated with [Claude Code](https://claude.com/claude-code)` footer.

**Put `Closes #N` (or `Fixes #N`) in the PR body** for every issue the PR fully resolves — one per issue — so the squash-merge auto-closes them. The `(#N)` *subject* suffix that squash-merging adds is **not** a closing keyword: it only links, it doesn't close. (This is how #19/#20 ended up implemented-but-open — their squash subjects referenced the issues but no body carried `Closes`.) For work that's blocked on or split across other issues, link them in prose instead of `Closes` so they stay open.

**A stacked PR stays a DRAFT until its parent merges.** When PR B is based on PR A's branch rather than on `main`, keep B in draft — GitHub disables the merge button on a draft, so this is a mechanical block on folding B into A's branch, not just a convention. Mark B ready only after A squash-merges, B is rebased with `--onto`, and its base has retargeted to `main` (GitHub retargets it automatically when A's branch is deleted on merge). Marking both ready at once is what makes the fold possible; a gate that unblocks A does not unblock B.

**Whichever way a stack resolves, `Closes #N` must end up on the PR that targets `main`.** Folding B into A's branch is a legitimate shortcut — it collapses the stack into one PR and skips the rebase — but it **silently orphans the keyword**: GitHub only auto-closes on merge to the *default* branch, so a `Closes` in B's body never fires and the issue stays open with no keyword anywhere on the PR that actually lands. Migrate it to A's body when you fold. (Hit on #147/#148: #148 carried `Closes #146`, merged into #147's branch, and #146 stayed open — the #19/#20 failure in a new shape.)

## Branching

Default/base branch is `main`. Do feature work on a topic branch (this repo has used names like `upstream-updates`); never commit directly to `main`. Rebase onto `main` to integrate upstream changes; squash-merge topic branches into `main` via PR. Stacked branches rebase with `--onto` after a parent squash-merges — and their PR stays a **draft** until then (see [Pull Request Format](#pull-request-format)).
