# MCP Server Architecture

Design rationale and research behind construct3-chef's MCP server (`src/mcp/server.ts`) and the file-based model it wraps. This is the durable reference; the operational summary lives in [CLAUDE.md](../../CLAUDE.md) (§ "The two-surface data model", § "MCP server state model"), and the tool-by-tool usage lives in [recipe-reference.md](../reference/recipe-reference.md), [generators.md](../reference/generators.md), [cli.md](../reference/cli.md), and [cli-addons.md](../reference/cli-addons.md).

> **Provenance.** construct3-chef began life inside the Genvid "burbank" monorepo as `bin/c3/` + `bin/mcp/`, developed across ~19 working sessions, then extracted into this standalone package (shared MCP plumbing → `@genvidtech/mcp-utils`, the C3 JSON domain layer → `@genvidtech/c3source`, domain-categorization tooling → `domain-manager`). That work was tracked in the now-retired **c3-mcp-server initiative**; its session-by-session plans, completed-feature design docs (packaging, filesystem-independence, session 18, SID-singleton removal), requirements analyses, and the full MCP security audit are recoverable from git history (`git log -- initiatives/c3-mcp-server`). The *forward-looking* parts of that initiative were carried into tracking issues: [#14 C3 Live Editor Integration](https://github.com/GenvidTechnologies/construct3-chef/issues/14), [#15 `extracted/` Generated On Demand](https://github.com/GenvidTechnologies/construct3-chef/issues/15), and the granular MCP-tooling follow-up issues (#18–#24).

## Why a file-based MCP server

The same library is exposed two ways — a yargs **CLI** and an **MCP server** — both thin wrappers over the pure functions in `src/c3/`. The MCP server gives Claude Code structured, queryable access to a C3 project (read DSL, search, apply recipes, regenerate, sync) without reading raw files or shelling out to `npm run`.

The decisive constraint is that **the C3 Editor SDK does not expose event-sheet or layout manipulation** (see [SDK capabilities](#c3-editor-sdk-capabilities-research) below). So the highest-value approach is a server that operates directly on the project's on-disk JSON, not one that drives a live editor. A live-editor bridge is *additive*, not essential — it is the subject of issue [#14 C3 Live Editor Integration](https://github.com/GenvidTechnologies/construct3-chef/issues/14).

```
Claude Code  <--stdio-->  MCP Server (Node.js, local)
                              ├── reads extracted/ files (DSL, scripts, layout summaries, indexes)
                              ├── reads eventSheets/ / layouts/ / objectTypes/ JSON
                              ├── applies recipes (mutates source JSON)
                              └── runs the 6 generators (regenerates extracted/)
```

## Design decisions

- **stdio transport over HTTP.** Claude Code launches the server as a subprocess and talks over stdin/stdout. Simplest setup, no port management, automatic lifecycle, no network exposure. (HTTP/WebSocket transports would add Origin validation and session-management burden for no benefit in a local dev tool.)
- **File-based first.** The SDK limitation makes file-based tools the primary value; the C3 Addon Bridge and browser automation are deferred until file-based usage reveals concrete gaps.
- **Wrap existing functions, don't duplicate logic.** The server calls the same exported `src/c3/` functions as the CLI. The boundary is deliberate: server code calls *exported* library functions (generators, recipe interpreter, project sync) rather than internal helpers, which is what made the standalone-package extraction a matter of packaging rather than refactoring.
- **`Logger` interface for output capture.** MCP stdio uses stdout for JSON-RPC, so any stray `console.log` from a called function would corrupt the protocol. Solution: a `Logger = (...args: unknown[]) => void` type (in `src/c3/types.ts`) threaded through every output-producing function. CLI entry points default to `console.log`; MCP handlers pass a line-accumulating closure and return the captured lines as tool text. No monkey-patching of `console`.
- **`ReadWriteLock` for concurrency safety, one instance per registered project.** The MCP SDK dispatches handlers concurrently, so two write handlers against the same project could interleave at any `await` and corrupt files. A write-preferring `ReadWriteLock` (from `@genvidtech/mcp-utils`) allows concurrent reads, exclusive writes, and queues new reads behind pending writes to prevent write starvation. It lives on `ProjectContext` (`ctx.rwlock`, see [Multi-project support](#multi-project-support) below), acquired in the handler body only — never by the `regP` registration wrapper, since `ReadWriteLock` has no owner tracking and a wrapper-held acquisition would nest inside the handler's own and hang. **The rule is exactly one lock acquisition per call, taken in the handler body** — `acquireRead`'s write-preferring guard deadlocks a nested *read* too, not only a nested write, so the rule is not scoped to mutate tools alone.
- **Terraform-like plan/apply via `txId`, wire-encoded per project.** A monotonic `txId` counter (owned by each project's own `OptimisticWatcher`, resets on restart) increments on every source-file write to that project. Validate/read tools return the current `txId`; `apply-recipe`/`sync-project` accept an expected `txId` and reject if it has moved (`"State changed: expected alpha:42, got alpha:43"`). The check-and-increment is atomic inside `rwlock.write()`. Prevents TOCTOU between validate and apply in multi-agent or user-concurrent scenarios. Under multi-project hosting the counter is emitted and accepted as a composite `<projectId>:<counter>` string (`src/mcp/txToken.ts`), not a bare integer — two projects sitting at an equal counter is the common case (both start at 0), so a bare integer would make a token minted for one project silently valid against another. See [Multi-project support](#multi-project-support).
- **Response shape: a single content block, adopted from upstream.** Every tool returns **one** text content block. Success-with-txId tools fold the result text and a trailing `txId: <n>` footer into one block via `@genvidtech/mcp-utils`' `mcpContent(text, footer)`; errors/rejections use `mcpError(e, { prefix, extraLines })` (`isError: true`, an `Error:` prefix, the `txId: <n>` footer as an extra line); a few txId-less paths (`regenerate`/`generate-sids`/not-found hints) emit `mcpError`/`mcpContent` without the footer. The handler bodies are wrapped in `withMcpErrors(fn, { prefix, onError, extraLines })`, which catches throws, runs the `onError` side-effect hook **before** formatting (hosting each tool's `CancelledError → watcher.bump()` / `extractedDirty = true` catch — `regenerate` is the exception: dirty-only, no bump), then formats via `mcpError` — its `extraLines` thunk runs *after* `onError`, so the `txId` footer reflects the post-bump value. This **replaces** the former local `errorWithTxId`/`caughtError`/`notFound` helpers and the old *two-block* (`text` + separate `txId`) shape. The split that once kept this local was settled the *other* way: **pagination adopted upstream first in [#26](https://github.com/GenvidTechnologies/construct3-chef/issues/26)** (`paginatedResponse` → `paginatedContent`, single block with the `lines: X-Y / total` footer, stale-warning folded in via the unchanged `appendStaleWarning`; out-of-range now reports the honest `lines: 0 / total`), accepting the client-visible contract-break as fine while the package is young. The error/txId shaping was the remaining holdout, blocked on three upstream capabilities (a `withMcpErrors` `onError` hook, a single-block `txId` footer, a configurable `Error:` prefix) filed as genvid-mcp-utils#5; **`@genvid/mcp-utils@0.4.0` delivered all three** (`mcpContent`, `mcpError`, `withMcpErrors` with `onError`), and [#25](https://github.com/GenvidTechnologies/construct3-chef/issues/25) adopted them on the back of the [#79](https://github.com/GenvidTechnologies/construct3-chef/issues/79) `^0.3.0 → ^0.4.0` bump. The two-block → single-block change is a **breaking** response-contract change (flagged for the next release tag). Both contracts are guarded by handler-level characterization tests (`test/mcp/serverHandlers.test.ts`), which invoke registered handlers directly via an internal `reg()` / `__getHandler` seam in `server.ts` against a fixture with a fake watcher — exercising the txId-rejection, stale-warning, single-block pagination ([#26](https://github.com/GenvidTechnologies/construct3-chef/issues/26)), and `CancelledError`-ordering paths ([#72](https://github.com/GenvidTechnologies/construct3-chef/issues/72), PR #73).
- **`extractedDirty` flag.** Tracks whether `extracted/` is stale relative to source. Set true on source writes or detected external changes (but not editor-local ones — see the watcher bullet below); cleared when `regenerate` (or `apply-recipe` with `regenerate: true`) completes. Read tools serving from `extracted/` append a staleness warning when dirty — they don't block or auto-regenerate (the agent decides). `checkSourceFreshness()` also flips it by comparing source vs. extracted mtimes, so a `git checkout`/editor-save/manual edit is caught even without a watcher event.
- **File-system watcher + self-write suppression, one watcher instance per context.** `createSourceWatcher` (`src/mcp/sourceWatcher.ts`) wires @genvidtech/mcp-utils' `OptimisticWatcher` over one project's source dirs + `project.c3proj`, assigned onto that project's `ProjectContext.watcher`. Watcher instances are never shared across contexts: `suppress()` guards its window with a per-instance depth counter, so a shared watcher would let one project's self-suppressed write blind another project's external-change detection for the duration of that window. External changes (editor saves, user edits) bump `txId` and set `extractedDirty` (source dirs), or bump `txId` only (`project.c3proj`); an external edit to an **editor-local** path (a live C3 editor's own `uistate/`/`ts-defs/`/`tsconfig.json` churn, per c3source's `isEditorLocalPath`) bumps neither — it's dropped at the **watcher factory**, before `OptimisticWatcher.handleEvent` (which bumps `txId` unconditionally ahead of the callback) ever sees it, since a filter placed in the callback could suppress `extractedDirty` but not the bump. This is the same non-source-file principle the ops registry already applies below via a wholly separate watcher, generalized here to editor-local state; see ADR [0018](../decisions/0018-editor-local-writes-are-not-source-changes.md) for the full rationale. To avoid double-counting the server's own writes, mutate tools wrap the write in `watcher.suppress(async () => { … })` (a synchronous suppress window) and, for events that arrive after the window closes, pre-register the path with `watcher.expect(absPath)` (a TTL-based `ExpectedChanges` set, periodically purged). **Editing a mutate tool means you must wrap its writes in `suppress` — and `expect()` any path written outside that call — or the watcher will spuriously mark state dirty.** `startServer` gives each registered project its own watcher and ops registry in a single per-project loop (`wireAllProjects`), and keeping both in that one loop is load-bearing rather than tidy: `ProjectContext.watcher` carries a definite-assignment assertion, so a context that never receives one holds `undefined` and throws on the first `ctx.watcher.txId` read — which is most of the tx-tracked surface. An earlier revision wired ops per-project but left the watcher call outside the loop, and every suite stayed green because the cross-project tests supply their own fake watchers; the regression guard therefore drives the real `wireAllProjects` against contexts deliberately given none. See [Multi-project support](#multi-project-support).
- **Cancellation leaves a coherent state.** Long tools check `extra.signal.aborted` between generator steps. A `CancelledError` mid-regeneration still sets `extractedDirty = true`, because source was already written before regeneration was interrupted.

## Concurrency & security posture

Summary of the standalone MCP security/best-practices audit (the full per-issue report is in git history under `initiatives/c3-mcp-server/mcp-audit.md`). Audited against the MCP spec (2025-03-26, 2025-06-18), security best-practices guide, and server-concept docs.

**In place:**

- **Path-traversal guards** (`path.relative()` + `startsWith("..")` containment) on every path-taking surface: `readExtracted`, `read-addon`, `scaffold-layout` (source + output), `scaffold-sprite`, and the `search` glob/path parameter. *Keep these when adding path-taking tools.* `search-docs` reads only `<extractedDir>/c3-reference/` (the local reference cache) and the project's own `addons/`; it never fetches anything and has no network surface. `diff-addon-aces` is a deliberate exception: its `.c3addon`-file-path source form is **not** containment-guarded to `--project-dir`, since the tool's purpose is diffing packages that live outside the project (e.g. a freshly downloaded release archive) — it stays read-only and its addon-id/dir source form still resolves (and containment-checks) through the same `resolveAddonTarget` the siblings use.
- **Optimistic concurrency** via `txId` (above).
- **Input validation** — Zod schemas on every tool, with `.describe()` on every parameter.
- **Two-tier error handling** — caught exceptions become `isError: true` content (a single block via upstream `mcpError`/`withMcpErrors`, see the response-shape bullet above); bad input surfaces as protocol errors.
- **Tool annotations** — every tool declares `readOnlyHint`/`destructiveHint`/`idempotentHint` via the `READ_ONLY` / `REGENERATE` / `MUTATE` constants.
- **ReDoS mitigation** on `search` — pattern length cap (500 chars) + match count cap (1000). (`re2` was deferred: a native dependency for marginal benefit against a local stdio threat model.)
- **Root resolution runs before `loadChefConfig`, once per registered project.** `startServer` resolves the launch surface (`src/mcp/launchConfig.ts`'s `buildProjectRegistry`) into an ordered `{id, root}` list, then constructs one `ProjectContext` per entry via `createProjectContext` (which itself calls `loadChefConfig`). For **zero or one** `--project-dir`/`C3_PROJECT_DIRS` spec, that resolution is the exact pre-multi-project call to `@genvidtech/mcp-utils`' `resolveRootFolder`, byte-for-byte, with its four levels of precedence: explicit `--project-dir` flag → `C3_PROJECT_DIR` env var → single-child `project.c3proj` discovery (immediate subdirectories, `searchDepth: 1`) → cwd. The env var is shared with the sibling c3-domain-manager server so one variable targets both. Explicit and env-var values are not path-contained (a `../sibling` root is valid); per-tool path guards still contain paths *relative to* the resolved root. On ambiguous discovery (≥ 2 child dirs each containing `project.c3proj`) or an I/O error, `resolveRootFolder` returns an mcpError; the server logs to stderr and falls back to cwd — consistent with the pre-existing warn-only posture for a missing `project.c3proj`. A cwd fall-through (no marker found) also emits a warning. In all cases, a `[construct3-chef] Root: <path> (source: …)` line is logged to stderr at startup. **Two or more** specs resolve every root explicitly instead — each gets a derived or `<id>=`-explicit id, with no `resolveRootFolder` call at all, since there is nothing left to discover (see [Multi-project support](#multi-project-support)). Non-server subcommands (`generate`, `apply-recipe`, etc.) default `--project-dir` to cwd exactly as before; the env-var, discovery, and multi-root steps are server-startup-only. Each `ProjectContext` carries its own `C3Project` handle (`openProject(root)` from `@genvidtech/c3source`, replacing the old module-level `PROJECT`); handler bodies and `src/c3/` functions use `ctx.project.eventSheetsDir`/`.layoutsDir`/etc. instead of `path.join(root, "eventSheets"|...)`. Three call sites were deliberately left on the old string-join pattern (see [wiki/decisions/0007](../decisions/0007-mcp-server-root-resolution-and-c3project-adoption.md) for the rationale); the `images/` gap (c3source#38) was resolved in `@genvidtech/c3source@1.6.0`, which added `imagesDir`.
- **Lifecycle** — stdio (no network surface), startup validation (warns on missing `project.c3proj` / `extracted/`, auto-generates `extracted/` when absent), graceful SIGINT/SIGTERM shutdown, MCP `logging` capability for watcher-event diagnostics.
- **`search-docs` has no network surface at query time.** It reads only the local `<extractedDir>/c3-reference/` cache and the project's own `addons/`. The PDF fetch + extraction that produces the cache is performed out-of-process by the gvt-construct3 `build-reference` plugin skill and is never an MCP tool — so the stdio server keeps its no-network-at-query-time posture.

**Known open items**: no cursor-based pagination on `list-event-sheets` / `list-layouts` ([#24](https://github.com/GenvidTechnologies/construct3-chef/issues/24); low priority at ~100 files). (The former configuration-layer gap, [#23](https://github.com/GenvidTechnologies/construct3-chef/issues/23), shipped across three phases — `extractedDir`, nav convention, and the `OpsRegistry` below.)

### Dynamic tool registration (`OpsRegistry`)

User-defined ops (#21 / #23 phase 3) add the one piece of *dynamic* tool surface to an otherwise static registry. `src/mcp/opsRegistry.ts`'s `OpsRegistry` loads parameterized recipe templates from a configurable directory (`ops.dir`, default `ops/`) and registers one `op-<projectId>_<opName>` MCP tool per file. **One `OpsRegistry` instance per registered project** (#95): `startServer` builds one for every entry in the `ProjectRegistry`, each constructed with `applyRecipe` closed over that entry's own `ProjectContext` — an op tool can therefore never reach another project's tree, structurally, not by convention. `list-ops` is no longer registered by `OpsRegistry` itself; it moved to a normal `regP`-registered tool in `server.ts` reading `ctx.ops.getLoadedOps()`, because a static per-context "list-ops" registration doesn't scale to N registered projects (N contexts would each try to register the same static name). Four things about how the surviving dynamic registration fits the concurrency model:

- **Op tool names bake in the owning project's id, not a `project` parameter.** `op-<projectId>_<opName>` — `_` rather than `-`, because op names match `/^[a-z0-9][a-z0-9-]*$/i` and project ids allow `-`, so `op-<id>-<name>` is genuinely ambiguous (project `a` + op `b-c` and project `a-b` + op `c` both yield `op-a-b-c`); neither charset admits `_`. This is deliberately unlike every other project-scoped tool, which takes an optional `project` selector via `regP` — an op tool's identity already pins its project, and it applies uniformly, including to the default project (no flat fallback form). Verified against the real MCP SDK (`tools/list`/`tools/call` both handle an underscore-bearing name) before committing. See ADR [0034](../decisions/0034-mcp-server-multi-project-support.md).
- **Its `fs.watch` is separate from the source `OptimisticWatcher`, per project.** Op files are not C3 source, so edits to them must NOT bump `txId` or set `extractedDirty`. Each project's registry runs its own debounced (~150 ms) `fs.watch` on that project's `ops.dir` (gated by `ops.watch`, default `true`; set `false` to disable where `fs.watch` is costly — ops are then scanned once at startup and a change needs a restart). A watch event triggers `reconcile()`, which diffs loaded ops against the registered set and adds / `update()`s / `remove()`s tools accordingly. The op-file watch never touches the source-write `suppress`/`expect` machinery, and one project's op-file churn cannot trigger another's reconcile — each `fs.watch` is scoped to its own `opsDir`.
- **Op handlers route writes through the shared apply path.** Applying an op = substitute `{{PARAM}}`s → a `Recipe`, then call `applyRecipeWithConcurrency(ctx, …)` — the same `ctx.rwlock.write` + `ctx.watcher.suppress` + `txId` bump + regenerate orchestration that backs `apply-recipe`, closed over the same `ProjectContext` the op's registry was built with (extracted into a shared helper for exactly this reuse). Op tools therefore inherit the full concurrency posture for free; only their *registration* is dynamic, not their write path.
- **`tools/list_changed` is SDK-driven.** The server declares `capabilities.tools.listChanged: true`; `@modelcontextprotocol/sdk`'s `registerTool` / `RegisteredTool.update()` / `.remove()` auto-emit `notifications/tools/list_changed` *only when connected* — so initial registration (before `server.connect`) is silent and post-connect reconciles notify automatically. The registry never calls `sendToolListChanged()` itself (that would double-notify). All registered projects' `OpsRegistry` instances are started before `server.connect()`, so every project's initial `op-*` tools are present from the first `tools/list` response.

## Multi-project support

One server process can host N C3 project roots; every tool call targets exactly one project. Full design record — the decision, all eleven declined alternatives, and the general one-lock-acquisition-per-call rule — is ADR [0034](../decisions/0034-mcp-server-multi-project-support.md). This section is the implementation-depth reference ADR 0005 points to.

- **Registry construction.** `src/mcp/launchConfig.ts`'s `buildProjectRegistry` resolves the launch surface (`resolveLaunchSpecs` + `resolveLaunchRoots`) into an ordered `{id, root}[]`, then constructs one `ProjectContext` per entry (`createProjectContext`, which composes `openProject`, `loadChefConfig`, `ReadWriteLock`, and `ExpectedChanges` — but deliberately **not** the `OptimisticWatcher` or `OpsRegistry`, both of which need a reference to the *finished* context and are wired on afterward by `startServer`) and adds each to a `ProjectRegistry`. The first resolved entry is the default unless `--default-project` overrides it.
- **The token codec.** `src/mcp/txToken.ts` is the single place that formats and parses the composite `<projectId>:<counter>` txId string: `formatTxToken(id, counter)`, `parseTxToken(s)` (a discriminated result, never `NaN`-propagating a malformed counter), and `compareTxToken(ctx, token?, action?)` — the optimistic-concurrency check every mutate tool performs, folded into one function so the id-mismatch and counter-mismatch error paths (and the `txId: <current>` footer both carry) are defined once. `undefined` passes unconditionally (the check stays opt-in, unchanged from pre-multi-project behavior); a token whose id doesn't match the call's resolved project is rejected **even when the counters are numerically equal** — the property a bare per-project counter cannot provide (see ADR 0034 decline 2).
- **Per-context lock/watcher topology.** Every `ProjectContext` owns its own `ReadWriteLock`, `OptimisticWatcher` (once wired — see the file-watcher bullet above for the v1 default-only caveat), `ExpectedChanges`, and `OpsRegistry`. None of these four is shared across contexts: the lock because two projects' writes must never serialize against each other's queue; the watcher because `suppress()`'s depth counter is per-instance; the ops registry because its `fs.watch` and `applyRecipe` closure are project-specific. `ExpectedChanges` is the one exception worth naming precisely — its keys are already root-disjoint absolute paths, so a single shared instance would serve N roots *correctly*; it stays per-context for uniformity with the rest of the container, not because sharing it would be unsafe.
- **Selector resolution (`regP`).** Every project-scoped tool's schema gains an optional `project` string param (`PROJECT_PARAM`); `regP` resolves it against the `ProjectRegistry` via a pure `Map` lookup (`REGISTRY.resolve(project)`) before calling the handler, so a handler body always receives an already-resolved `ProjectContext` — never a module-level default it has to remember to read from. `list-projects` is the sole tool on plain `reg`, since it enumerates the registry itself and cannot belong to one project.
- **The one-acquisition-per-call rule.** `regP` deliberately does not acquire `ctx.rwlock` — see the `ReadWriteLock` bullet under [Design decisions](#design-decisions) above for why a wrapper-held lock would nest inside a handler's own acquisition and hang. The rule generalizes past this specific wrapper: any code path that could call into a lock-acquiring function from inside another lock-acquiring function on the same context is the same hazard, whether or not `regP` is involved.

## C3 Editor SDK capabilities (research)

Findings from the C3 addon SDK exploration that justify the file-based-first decision. The editor-side SDK **exposes**:

- Instance manipulation (create/delete instances in layouts; set position/size/rotation/properties)
- Object types (create object types; access animations/frames)
- Plugin properties (`GetPropertyValue`/`SetPropertyValue`)
- Custom editor rendering (`Draw()` for layout-view visuals), file importers (drag-drop ZIP/Blob)
- Undo/redo (`UndoPointChangeObjectInstancesProperty`), project access (`layoutView.GetProject()` → `IProject`)
- Single-global plugins that persist across layouts (ideal for service integrations)

It does **not** expose — and this is the crux — **event-sheet read/write, layout-structure manipulation (layers, layout properties), variable/data manipulation, project filesystem access, or direct inter-plugin communication.** Editor-side code runs on the main browser thread (has `fetch`/`WebSocket`); runtime code uses a DOM messaging bridge (`postToDOM`/`postToDOMAsync`).

**Consequence:** anything touching event sheets or layout structure *must* go through the on-disk JSON (the file-based server). A live bridge can only add instance/property manipulation on top — which is exactly the scope of issue [#14 C3 Live Editor Integration](https://github.com/GenvidTechnologies/construct3-chef/issues/14).

### C3 addon structure (reference)

An addon is a `.c3addon` ZIP with `addon.json`, `aces.json`, editor scripts (`plugin.js`/`type.js`/`instance.js` over `SDK.IPluginBase` etc.), `c3runtime/` (actions/conditions/expressions/`domSide.js`), and `lang/`. Runtime↔browser communication goes through a `_postToDOM(message, data)` DOM bridge. The single-global pattern (one instance, persists across layouts) is the right shape for a service integration such as an MCP relay.

## Prior art: liauw-media/construct3-mcp

[github.com/liauw-media/construct3-mcp](https://github.com/liauw-media/construct3-mcp) — an MIT-licensed, from-scratch MCP server for C3 projects with its own reader/writer, SID/UID generation, analysis tools, and mutation operations. A full architectural comparison (their type model, analyzers, mutation orchestrator) is preserved in [prior-art-construct3-mcp.md](./prior-art-construct3-mcp.md).

**What they have that construct3-chef does not:**

- Event-sheet flow visualization and function mapping
- Dependency graphs and orphaned-object detection
- Asset-usage tracking and performance heuristics
- Imperative event-block mutation tools (add condition / add action / create block)
- Automatic backup before mutations

**What construct3-chef has that they do not:**

- Human-readable DSL with cross-references; extracted TypeScript with named scope types
- Layout summaries and template-scope reference
- A declarative recipe system (batch mutations, builder shorthand)
- DSL index for SID ↔ JSON-path ↔ line lookup

**Takeaways:** their event-flow analysis attacks the same readability problem the DSL was built for, by a different route (structured queries vs. human-readable text) — both valid. Their imperative "add action / add condition" model is simpler for one-off edits; construct3-chef deliberately chose declarative recipes, which shine for batch operations but are heavier for a single tweak. Their analyzers (deps, orphans, asset usage, performance) are the clearest source of ideas for future read-only tooling.
