# Leaf-dependency ledger

The version-by-version record of `@genvidtech/c3source` and `@genvidtech/mcp-utils`: what each upstream release shipped, what construct3-chef adopted, what it deliberately declined, and the evidence behind each call. Split out of `CLAUDE.md` § "Leaf dependencies" in [#172](https://github.com/GenvidTechnologies/construct3-chef/issues/172); see ADR [`0026`](../decisions/0026-leaf-dependency-ledger-split-from-claude-md.md).

**What goes where.** `CLAUDE.md` is loaded into every session automatically; this file is not. The *posture* — the rules for deciding an adoption, which hold no matter which version is pinned — stays in `CLAUDE.md` § "Leaf dependencies". The *record* — what a particular release did and what we did about it — belongs here. The routing test for a new version fact: **if it would need editing when the next version ships, it belongs here; if it survives every version unchanged, it belongs in `CLAUDE.md`.**

**Entries never assert which pin is current.** `package.json` is the authority. An entry records, in the past tense, what a release shipped and what chef did about it.

**Ordering.** One section per package, entries oldest first. A new entry is appended to the end of its package's section as a new `###` heading — never merged into an existing entry.

**Before adopting a new upstream release, read that package's newest entry here.** The deliberate declines are recorded rather than silently skipped, and the newest entry names what to check at the next bump.

## @genvidtech/c3source

### 1.0.0

 A detection-only/flat upstream API can't back a *mutating, nested* op: #42 adopted c3source's editor-local *fact* (`isEditorLocalPath`) and manifest *parse* (`readProjectManifest`), but could **not** route `projectSync.runSync` through `detectManifestDrift` — that returns flat bare-name drift with no subfolder path, so it can't locate where to mutate the nested two-way sync (it also omits `families` and models `objectTypes` as flat files). Rather than force a net-positive adoption with the wrong shape, the right move was to request the structured primitive upstream and wait: c3source#21 delivered a path-bearing `SectionDrift`/`DriftEntry` API (carrying `manifestPath`/`diskPath` segments, a `kind` enum, `families` coverage, and directory-aware `objectTypes`) in c3source 1.0.0. `projectSync.runSync` now routes name-section sync through `detectManifestDrift` + a local `applyNameDrift` apply engine, closing #47 and removing ~250 lines (the deferred "+30–60 / 0 removed" became a net-negative adoption once the shape fit). File sections stay local — file-section SID minting needs ext-bearing disk names that `detectManifestDrift`'s file coverage doesn't reliably give. `detectImageDrift` is surfaced as a detection-only `[images]` report in `validate-project` (never a sync write-back target — images aren't manifest entries; tracked by #52). The breaking `readDiskDirNames`/`syncNameFolder` removals (both re-exported from `src/index.ts`) are flagged for the next release tag. 

### 1.1.0

**c3source 1.1.0** then added `extractIncludes` (a `visitEvents`-based include walk) and enriched `extractFunctions`/`ExtractedFunction` (now carrying `params`/`returnType`); both are adopted in `includeTree.ts` — `extractIncludes` replaced a top-level-only include walk (closing a latent nested-include gap), and the include-tree function listing now renders full signatures from the enriched data (rendering stays local). The local `extractFunctions(events)` keeps its `string[]` *type* signature; only the emitted string *content* changed (signature tail), so it's not a type break. 

### 1.2.0

The intervening **c3source 1.2.0** added an `isEventVarReference`/`getEventVarReferenceName` event-variable-reference classifier — **not yet adopted** (no consuming op needs it today); it's available for a future adoption if event-var-reference detection is wanted in the DSL/index surface. 

### 1.3.0

**c3source 1.3.0** (adopted via a single `^1.1.0`→`^1.3.0` bump) fixed two critical drift bugs in the format model that construct3-chef inherits transparently through the `detectManifestDrift`/`detectImageDrift` it already consumes: c3source#28 (a timeline's on-disk `transitions/` directory serializes as an **unnamed** subfolder under `timelines`; the manifest walk now models that — closing our #62, which had been masked as 3 "pre-existing" Windows `syncC3Proj` timeline failures) and c3source#29 (image members resolve their on-disk extension from the declared `fileType` MIME, not an assumed `.png` — closing our #63). One **downstream guard** was needed: c3source#29 makes an absent/unmapped `fileType` *throw*, and `detectManifestDrift` wraps `detectImageDrift` in a try/catch but our **direct** `reportImageDrift` call doesn't — so `reportImageDrift` now catches and reports an `[images] error: …` line instead of crashing `validate-project`. Fixture coverage for both fixes was added by mirroring c3source's own `c3source-fixture` (a populated `timelines/transitions/Matt's Ease.json`; a JPEG-backed `JPEGTileBackground` object + `LevelMaps` family), and the fixture was renamed `sample-project`→`construct3-chef-sample` (#64). 

### 1.4.0

**c3source 1.4.0** (adopted via `^1.3.0`→`^1.4.0`) delivered `validateForEditor`/`validateEventForEditor`/`EDITOR_FIELD_RULES` — the c3source#33 deliverable — and is adopted in two places: (1) a private `assertEditorValid` helper in `recipeApplier.ts` runs it on every event sheet at the `writeEventSheet` chokepoint, hard-failing (throwing with jsonPath + rule id) before any write if a node would make the C3 editor reject the project on import (covers `apply-recipe` write-out and `validate-recipe` dry-run preview; closes #84); (2) `test/c3/fixtureLoadValidity.test.ts` runs every fixture event sheet through `validateForEditor` and asserts zero issues (closes #61). `assertEditorValid` is **not** on the `src/index.ts` barrel — no new public API.

### 1.5.0 and 1.6.0

**c3source 1.5.0** added `openProject(root): C3Project` — a root-bound handle exposing the canonical source-subfolder dirs (`eventSheetsDir`/`layoutsDir`/`objectTypesDir`/`familiesDir`/`scriptsDir`), `has*()` checks, a lazy cached `manifest()`, and rooted `findAll*` finders (it unifies c3source's previously-split API, where the `find_all_*_path` finders took a *subfolder* but the drift/manifest helpers took the *root*). Adopted in #94 (the c3source#36 deliverable) to replace ~32 scattered `path.join(PROJECT_ROOT, "eventSheets"|…)` literals with `PROJECT.eventSheetsDir` / `.findAllLayouts()` etc. via a module-level `PROJECT` handle beside `PROJECT_ROOT`/`EXTRACTED_DIR` — **strategy (c) "Hybrid"**: a value-preserving internal refactor (the `*Dir` fields are plain string joins, no I/O, so output is byte-identical — locked by an equality test) with **no barrel-signature change** and zero golden risk. **Deliberately NOT** routed through the handle (record before "fixing" them): `sourceWatcher.SOURCE_DIRS` (already an SSOT array), the `projectSync` section configs (model 12 disk dirs + per-section metadata + feed the c3source drift API — exceed the handle's 5 dirs), and the barrel-exported `SID_SOURCE_DIRS` (deliberately excludes `families/`). The `images/` gap (c3source#38) was resolved in `@genvidtech/c3source@1.6.0`, which added `imagesDir` to `C3Project`; the two `path.join(root, "images")` literals in `cli.ts`/`server.ts` are now migrated to `PROJECT.imagesDir` / `openProject(rootDir).imagesDir`.

**c3source 1.7.0** (adopted via `^1.6.0`→`^1.7.0`, closes #101) completed the `C3Project` handle (c3source#40), adding the remaining section/asset dirs (`timelinesDir`/`flowchartsDir`/`models3dDir`/`soundsDir`/`musicDir`/`videosDir`/`fontsDir`/`iconsDir`/`filesDir`) plus matching `has*()`/`findAll*()` and exporting `C3_SECTION_FOLDERS`/`C3_ROOT_FILE_FOLDERS` maps. Adopted minimally: the three `path.join(rootDir, "scripts/ts-defs/…")` literals in `recipeApplier.ts` now route through `openProject(rootDir).scriptsDir` (the last section-dir literals not yet on the handle after #94/#102); the deliberately-left sites stay literal (`sourceWatcher.SOURCE_DIRS`, `projectSync` section configs, `SID_SOURCE_DIRS`). The same bump delivered `COMPARISON_OPERATORS`/`comparisonSymbol(n)` (c3source#42) — a comparison-operator domain fact; the upstream DSL renderer (`formatCondition`/`formatAction`, which `dslFormatter.ts` delegates to) now annotates `comparison` ACE params with their operator symbol (e.g. `comparison=4 (>)`), inherited **transparently** — no local render change. ### 1.8.0

**c3source 1.8.0** (floor bumped via #131/PR #135) then shipped two things: the expression tokenizer `extractExpressionReferences` (c3source#43, the direct #123 blocker) and a `.c3addon` **domain layer** (c3source#44 — `readAddonPackage`/`AddonPackage`, `parseAcesModel`/`AcesModel`, `parseAddonMetadata`, `aceIdentity`/`findAce`/`findExpression`, `collectAddonAttribution`, `findAllAddons`, `stripBom`/`C3ADDON_EXTENSION`). The `.c3addon`-layer adoption (#136, ADR `wiki/decisions/0014`) is **deliberately partial**: chef adopted only `stripBom` (replacing the #124 BOM fix), `aceIdentity` (deduping two local `aceKey` copies in `addonAceDiff`/`addonAceUsage`), `C3ADDON_EXTENSION` (extension-matching literals), and a **new additive `readAddonAcesModel(addon): AcesModel`** seam in `addonReader.ts` (the `DiscoveredAddon → AcesModel` hook #123 consumes for `findExpression`). The **bulk stays local on per-module shape-fit grounds** (record before "fixing"): the hybrid reader (upstream `readAddonPackage` picks one form at construction + directory mode is top-level-only, so it can't back chef's per-entry dir→zip fallback or nested `lang/*.json` reads); `mapAcesJsonToEntries`/`AceEntry` (carries `objectClass`, renames params, per-category-interleaved emit order vs upstream group-by-kind → reorder breaks `formatAddonInfo` byte-identity; upstream throws vs chef per-entry-tolerant); `readAddonMetadata`/`readUsedAddons`/`readObjectDefn` (all tolerant/all-optional vs upstream strict-required + throwing — the `ObjectType`/`Family` parse-type dedup was scoped in but **dropped** on exactly this mismatch); `findAllAddons` (no kind-by-subdir); and all formatters/operations. `customAceIndex.ts` is out of scope (reads event-sheet custom actions, not `.c3addon`). 

### 1.9.0

**c3source 1.9.0** (`^1.9.0`, installed and locked at 1.9.0) shipped an optional third **`descend` parameter** on `find_all_files_path` — `find_all_files_path(dir, predicate, descend?: (dirname: string) => boolean): string[]`, defaulting to `descendSourceDirs` (`!isEditorLocalPath(name)`), which controls directory *reachability* separately from the `predicate`'s file selection; it is a **parameter, not a top-level export** (#146's title is loose on this) — plus `custom-ace-name-required` (a new `EDITOR_FIELD_RULES` entry) and `detectReferenceIntegrity`. **The adoption did not justify the bump; `custom-ace-name-required` did**: it reaches chef's `assertEditorValid` write chokepoint as a new pre-write guard on **both** `apply-recipe` and `validate-recipe`, with its first real-data coverage arriving via the v0.7.0 fixture's `custom-ace-block`; the rest of the 1.9.0 export surface is purely additive. **Adopted** (#146): `find_all_eventsheets_path` in `includeTree.buildSheetNameMap` — the last hand-rolled event-sheet walk in the repo, which had accepted every `.json` with no editor-local filtering at all. The *named* collector carries the editor-local predicate, so both the `uistate/` directory prune and the `*.uistate.json` sibling rejection come for free; only the project-root-relative POSIX path normalization stays local (rendering, per ADR `wiki/decisions/0006`). ⚠️ The sting worth recording: that collector **shipped in 1.8.0**, so the adoption never needed the 1.9.0 bump at all — and it was a **drift fix, not a bug fix** (the defect was latent and unreachable). **Declined** — the full triage argument lives in ADR `wiki/decisions/0016` (and `0019` for why the *same* primitive is adopted elsewhere: these are site-scoped declines, not a blanket rejection of c3source's walk), don't re-derive or re-state it: `generators.findJsonFiles` stays on mcp-utils' `walkFiles`; `projectSync.readDiskDir` stays local; the **`descend` parameter itself has no consumer in chef** — `ts-defs/` is reached by two hardcoded filenames, a tsconfig `include` glob string, and a skip, so there is no walk to parameterize (recorded explicitly so nobody invents one to justify the parameter); and `detectReferenceIntegrity` stays unadopted on a deliberate **ownership split** — upstream owns the declared-`usedAddons` ↔ used-in-source edge, while the `.c3addon`-package ↔ `usedAddons` direction stays chef's (`addonValidator.ts`, `addonInventory.ts`), recorded so the split stays intentional rather than looking like an oversight. 

### 2.0.0

**c3source 2.0.0** (`^2.0.0`, installed and locked at 2.0.0) shipped **two breaking changes**, adopted in [#175](https://github.com/GenvidTechnologies/construct3-chef/issues/175). **(1) The `.json` item policy** (c3source#76): `find_all_layouts_path`/`find_all_objectTypes_path` — and the `C3Project` methods over them — now return only `.json` section items via a new `find_all_section_items_path`, where they previously returned every non-editor-local file. Chef inherits this as a **pure fix with zero code change**: **ten** sites piped those finders straight into `JSON.parse` with no `.json` guard (`generators.ts:357`/`:426`/`:472`, `layoutScaffold.ts:77`, `navigationGraph.ts:12`, `projectObjects.ts:79`/`:159`, `recipeApplier.ts:331`/`:350`, `templateLister.ts:10`), each of which would have thrown `SyntaxError` the first time a stray non-`.json` file appeared under `layouts/` or `objectTypes/`. Two asymmetries worth not flattening: `recipeApplier.ts:331` is only *partially* unguarded — `findObjectTypeFile`'s `basename(p, ".json") === typeName` filter means it crashes only on a stray named **exactly** `<TypeName>` with no extension — and an **11th consumer changes *behaviour*, not crash-safety**: `server.ts`'s `list-layouts` renders finder output without parsing, so a stray non-`.json` under `layouts/` no longer appears in the MCP tool response (no CLI counterpart exists). ⚠️ **The fix is free; the proof is not.** The canonical fixture tracks zero stray files, so a fixture-based assertion passes **vacuously at both floors** — the #149/ADR 0020 shape again. Coverage is the synthetic temp-dir `strayFileTolerance` suite, which drives *chef's own consumers* rather than the upstream finder (asserting on `find_all_layouts_path` would test c3source, whose own suite covers it), and which was **committed red at the 1.9.0 floor before the bump landed** — making the revert-confirm structural and visible in git history rather than a step someone claims to have run (0 passing/8 failing at 1.9.0, 8 passing at 2.0.0; re-run after the test's final edit, so it holds for the committed code and not an earlier draft). **(2) Dotted extensions** (c3source#73/#74) — every extension-valued domain fact now carries a leading dot (`C3_LEGACY_IMAGE_EXTENSION`, `IMAGE_FILE_TYPE_EXTENSIONS`, `SCRIPT_FILE_TYPE_EXTENSIONS`, `ExpectedImage.ext`). **Audited and a verified non-event for chef** — no `src/` file imports any affected symbol, and the one test-side consumer (`deriveExpectedImageNames`) emits a byte-identical string because the dot merely moved into the constant; recorded so the audit is not reopened, since the issue originally flagged it as needing one. **Declined, and don't re-derive it — see ADR [`0021`](../decisions/0021-section-item-axis-does-not-reopen-walk-declines.md)**: the new both-dimension `find_all_section_items_path` does **not** reopen ADR 0016's three declines (`readDiskDir`, `findJsonFiles`, the `descend` parameter), because `find_all_files_path` is **unchanged** between 1.9.0 and 2.0.0 and the `findJsonFiles` decline's three cost objections (throws where `walkFiles` swallows `ENOENT`; per-entry `statSync` turning a per-file TOCTOU into a whole-directory abort at `server.ts`'s freshness scan; imposed ordering) survive verbatim on symbols barrel-exported at 1.0.0. ⚠️ Record the honest part too: that decline's *"buys nothing"* leg **is** now gone — upstream previously offered only the reachability axis and now classifies both dimensions — so it rests on the three costs **alone**. What would actually reopen `findJsonFiles` is an upstream walk carrying `walkFiles`' **error tolerances**, not a further named axis; that is the concrete thing to check at the next bump. **Adopted as a detection-only report ([#177](https://github.com/GenvidTechnologies/construct3-chef/issues/177), ADR [`0023`](../decisions/0023-stray-files-are-a-detection-only-report.md)):** `detectStrayFiles`/`StrayFile` — the other half of the item-policy trade, since the finders now *skip* a stray where they used to crash on it, which is quieter, not louder. `projectSync.ts`'s `reportStrayFiles(rootDir, log)` renders `[strays]` lines in the same `padEnd(16)` label column as `[images]` and is wired at the **four** `[images]` surfaces (CLI + MCP `validate-project`/`sync-project`) and deliberately **not** at the four `runSync` sites without `[images]` (scaffold-layout/scaffold-sprite). It is informational **by default** at every surface — it moves no `SyncResult.clean` and no `ManifestDrift.inSync`, though the CLI's `validate-project --fail-on-strays` opts into a failing exit code (#183) — and is never a sync write-back target, per the `detectImageDrift` precedent and because a stray has no manifest position and can never acquire one. It **always emits one line** (`(no strays)` on a clean project): silence would render "no strays" and "reporter absent" identically, the unfalsifiable-green shape this repo has shipped twice. It covers all seven upstream name sections **including `models3d`**, which chef's own sync excludes — reporting is not syncing, and filtering to chef's six would re-derive a section list upstream owns (the ADR 0016 mistake) — and is **not** narrowed by `--section`, which scopes the write-back only (the `[images]` precedent). It calls `detectStrayFiles` **standalone** rather than reading the `ManifestDrift.strays` value `runSync` already receives and drops; the two routes yield byte-identical data (⚠️ #177's framing that the drift route would *inherit* `--section` is mechanically wrong — `runSync` calls `detectManifestDrift` with no section argument and filters its *result*), so the real trade is one OS-cached duplicate walk versus either emitting inside `runSync`'s eight call sites or permanently widening the barrel-exported `SyncResult`; calling directly also keeps the report manifest-independent, which `runSync` is not. An `extractedDir` nested under a section root (e.g. `"layouts/extracted"`) **is** reported — upstream's own canonical stray example is `layouts/Level1.dsl.txt` — so keep `extractedDir` outside the seven roots; output caps at 20 rows plus a `… and N more (M total)` tail because neither MCP tool paginates. `reportStrayFiles` is public API at 1.0.0 on landing (barrel-wholesale re-export), so the name is decided once; `STRAY_REPORT_LIMIT` stays module-private. Chef's colliding local vocabulary was renamed instead of upstream's term: `syncC3Proj.test.ts`'s `Stray.json` fixture is now `Untracked.json`, matching `DriftEntry.kind`. Both follow-ups shipped in ADR [`0025`](../decisions/0025-stray-gating-is-cli-only-and-survives-a-manifest-failure.md): [#183](https://github.com/GenvidTechnologies/construct3-chef/issues/183)'s `--fail-on-strays` is CLI-only and opt-in, with **no MCP gating counterpart** by design (`isError` stays reserved for genuine tool failure); [#184](https://github.com/GenvidTechnologies/construct3-chef/issues/184) makes `[images]`/`[strays]` survive an unreadable/unparseable `project.c3proj` on both surfaces, since both reporters are manifest-independent by construction. `reportStrayFiles` now returns `StrayFile[]` (the full detected set, not just the capped rendering).

## @genvidtech/mcp-utils

### 0.3.0

The configuration-layer design (#23) factored its generic config **loader** — read a JSON file at project root, zod-validate against a caller-supplied schema, merge init-overrides, path-contain via the existing `resolveWithin` — out as a request for **`loadProjectConfig<T>`** on `GenvidTechnologies/mcp-utils` (mcp-utils#3), shared with c3-domain-manager (c3-domain-manager#7). That loader **shipped in `@genvid/mcp-utils@0.3.0`** (`loadProjectConfig`/`isMcpError`/`LoadConfigOpts`, errors-as-values) and is **adopted in #23 phase 1**: `src/c3/chefConfig.ts`'s `loadChefConfig` wraps it to load `construct3-chef.config.json` and make the `extracted/` dir name configurable (`extractedDir`). Local stayed local exactly as planned — the `ChefConfig` schema is in-repo (and *not* on the `src/index.ts` barrel). **#23 phase 2 (#43) then shipped** `resolveNavConvention` in `src/c3/navConvention.ts` (also off the barrel): `navigation-graph` is no longer hardwired to a project-specific `GoToLayout` wrapper — it defaults to detecting the built-in `System.go-to-layout` / `go-to-layout-by-name` actions (rendered as `System.go-to-layout(layout=…)` / `…-by-name(layout="…")`, per the `construct3-chef-sample` fixture) and is overridable via `navigation.targetPatterns` (capture-group regexes) + `navigation.definitionMarkers`. The default scans the System action only (a wrapper is *implemented with* those calls, so scanning both would double-count); a bad regex is dropped without taking down the rest of the config. `findGoToLayoutCalls` gained a trailing optional `convention` param (additive/non-breaking) and its DSL header parse was widened from `\S+` to capture spaced sheet names. **#21 / #23 phase 3 shipped** the `OpsRegistry` dynamic-tool registrar (`src/mcp/opsRegistry.ts`): user-defined op files (`.json`) in a configurable `ops/` directory each become a typed MCP tool `op-<name>` and a CLI `apply-op <name>` command; `list-ops` enumerates them on both surfaces using a shared `formatOpsList` formatter (`src/c3/opTemplate.ts`); the MCP server hot-reloads op tools when the ops dir changes (`ops.watch: true`, default). The `ChefConfig` schema gained an `ops: { dir, watch }` block (defaults `"ops"` / `true`); an escaping `ops.dir` falls back to `<root>/ops`. See `wiki/reference/ops.md` for the op file format and substitution rules. 

### 0.4.0

Beyond the config layer, the MCP **response-shaping** helpers were also adopted from mcp-utils: **#26 (PR #77)** replaced the local single-block pagination with `paginatedContent` (`paginatedResponse` now joins the page text + `lines: X-Y / total` footer in one block, stale-warning folded in via the unchanged `appendStaleWarning`, out-of-range reports the honest `lines: 0 / total`), and **`@genvid/mcp-utils@0.4.0`** then delivered the error/txId trio — `mcpError`, `withMcpErrors` (with an `onError` side-effect hook), and `mcpContent` — that **#25** was gated on (filed upstream as mcp-utils#5). **#25 (on the back of the #79 `^0.3.0 → ^0.4.0` bump, PR #80)** retired the local `errorWithTxId`/`caughtError`/`notFound` formatters and wrapped every handler in `withMcpErrors`, so **all** tool responses are now a single content block: success folds `txId: <n>` into the block via `mcpContent`; the `CancelledError → watcher.bump()`/`extractedDirty` catches live in per-tool `onError` hooks (which run *before* the `extraLines` txId thunk, preserving `bump → read-txId` ordering); `regenerate` stays the exception (dirty-only, **no** bump, no txId footer). The two-block → single-block change is **breaking** (flag at the next release tag). This closes the pagination-vs-error split the *other* way from the #23-era "response shaping stays local" call — once the package grew the capabilities, the shaping moved upstream, per the young-package adoption bias (see `wiki/architecture/mcp-architecture.md` response-shape bullet). Note the audit-era "MCP audit:" issues can name hardcodes belonging to a *sibling* project — #23's `domain-config.json` was actually c3-domain-manager's — so grep this repo before designing a fix. 

### 0.5.0 and 0.5.1

The same posture governs **`@genvid/mcp-utils@0.5.0`**, which added `resolveRootFolder` (generic `explicit > env > discovery > cwd` project-root resolution, errors-as-values, no containment on explicit/env) — adopted in #94 (the mcp-utils#7 deliverable) to fix the MCP server's nested-project targeting: precedence `--project-dir` > `C3_PROJECT_DIR` env var > single-child `project.c3proj` discovery > cwd, where **`C3_PROJECT_DIR` is shared with the sibling c3-domain-manager server** so one env var targets both. Ambiguous discovery / I/O error logs to stderr and falls back to cwd (no exit, no client connected yet). The full rationale (including the rejected adoption strategies (a)/(b)) lives in ADR `wiki/decisions/0007-mcp-server-root-resolution-and-c3project-adoption.md`. 

### 0.6.0

Bumped `@genvidtech/mcp-utils` from `^0.5.1` to `^0.6.0`, adopting its `walkFiles` fix: every returned path is now guaranteed to be a regular file — directories, directory symlinks/junctions, broken symlinks, and cycles are never emitted even when their name satisfies the predicate, while a symlink resolving to a regular file still is. This was a **real bump, not adoption**: `^0.5.1` resolves to `>=0.5.1 <0.6.0-0`, so the range excluded 0.6.0 and the new behavior was neither installed nor callable until the lockfile refresh. (CHANGELOG.md; #168)

Evidence (#168, mcp-utils 0.6.0): `walkFiles` began guaranteeing every returned path is a regular file, which overlapped `search()`'s local `statSync` clause. Deleting that clause left **38 passing, 0 failing** — including a test literally named *"does not throw EISDIR when a directory junction sits under `layouts/`"*, which now passed because upstream filtered the entry rather than because the clause did. The clause was still load-bearing for the two single-file branches that never call `walkFiles`, so dropping it — as both the code comment and ADR 0020 then advised — would have reshipped the crash through a fully green gate. 

Three call sites were fixed transparently with no local code change — `generators.findJsonFiles`, `spriteScaffold.findSourceJsonFiles` (via `collectAllObjectTypeSids`), and `cli.ts`'s `search-dsl` (left uncovered: it is inline in the yargs handler, with no exported seam). The local `statSync` clause in `search()` was **kept** rather than dropped, correcting both ADR 0020's and the `keep()` comment's advice to remove it once mcp-utils#10 landed — the two single-file branches never call `walkFiles`, so upstream's guarantee cannot reach them. This bump is what produced the revert-confirm rule now stated in `CLAUDE.md` § "Leaf dependencies". (#168)

### 0.7.0

**mcp-utils 0.7.0** (`^0.6.0`→`^0.7.0`) adds **Layer 3** to `OptimisticWatcher`: a per-path content-fingerprint ledger (`ObservedState`, sha1 over file bytes, LRU-bounded at `maxEntries` default 1000) that collapses duplicate filesystem events for unchanged content. It fixes a Windows/NTFS defect where a single `writeFileSync` delivers two `fs.watch` events, so `txId` counted watcher events rather than logical changes. A **real bump, not adoption** — `^0.6.0` resolves to `>=0.6.0 <0.7.0-0`, so the range excluded 0.7.0, the same shape the 0.6.0 entry above already establishes for this package. Chef adopted it with **zero `src/` change**: `OptimisticWatcher`'s constructor builds a default `ObservedState` when `options.observed` is omitted, and `createSourceWatcher` (`sourceWatcher.ts`) constructs `OptimisticWatcher` with no `observed` key, so Layer 3 applies transparently. Native Windows paths stay correct under it — `ObservedState.record`/`isChanged` apply `toPosixPath` only to the map key and pass the raw `filePath` to `readFileSync`, leaving chef's deliberate native-Windows-path watcher factory untouched. Layer 3 fails open by design: eviction from the LRU bound, a throwing fingerprinter, or an unreadable file all degrade toward an *extra* bump, never toward suppressing a real change — the one failure this design does not tolerate.

Revert-confirm (per `CLAUDE.md` § "Leaf dependencies") found **no** overlapping local guard — a genuine negative result, unlike #168's mcp-utils 0.6.0 bump above, where the same rule found `search()`'s `statSync` clause overlapping and load-bearing. The one plausible overlap, chef's editor-local `filteringFactory` in `sourceWatcher.ts`, was checked by mutation rather than by reasoning: disabling the filter took the suite to 8 passing / 3 failing, exactly the three editor-local dimension tests — so those guards still guard, because the filter is a *classification* concern Layer 3 never touches. The `watcher.expect()` call sites — `clone-layout`'s and `scaffold-sprite`'s handlers in `server.ts`, both already inside a `suppress()` window — carry no duplicated-path workaround to retire, and `opsRegistry`'s debounce belongs to a separate watcher, not `OptimisticWatcher`. (Named rather than counted deliberately — see `CLAUDE.md`'s eighth grep trap, which this clause is the evidence for.)

**Accepted gap, flagged for the next bump.** The manual Windows verification the issue proposed was dropped by decision; stub coverage against the injected test factory was treated as sufficient instead. Consequence: nothing locally confirms that native `fs.watch` actually delivers duplicate events on Windows/NTFS rather than the duplicates being collapsed earlier by chance before they ever reach `OptimisticWatcher`. Chef's coverage proves the *collapsing behaviour*, not the *duplicate delivery* — check this at the next bump if the trigger mechanism itself is ever in question.

The issue's framing — that a manual Windows run was "the only real confirmation" — conflates two things. The **trigger** (NTFS delivering two raw events per write) is genuinely Windows-only and untestable on Linux CI. The **behaviour** (collapsing same-content duplicates once two events do arrive) is platform-independent and reachable through the injected stub factory `sourceWatcher.test.ts` has used since it was written. The reusable rule: *a platform-specific trigger does not imply platform-specific testability — inject at the seam.* See ADR [`0027`](../decisions/0027-cross-platform-stub-coverage-over-manual-windows-verification.md).

The pre-existing 9 `sourceWatcher.test.ts` tests pass **unmodified** at 0.7.0, but they were structurally incapable of observing the fix: each fires its path exactly once, and `build()` constructs a fresh watcher per test, so Layer 3 always saw `prev === undefined` and bumped regardless. New coverage was therefore required, not merely nice to have. **Declined:** `observed: null` (forfeits the fix entirely — no fingerprint ledger at all) and a custom `stat`-based `Fingerprinter` (upstream measured `size:mtimeMs` colliding on distinct same-size writes within one timestamp tick, and a fingerprinter that compares equal on different content makes Layer 3 suppress a real change — staleness, the failure the design exists to avoid; this is why no `stat`-based fingerprinter ships upstream at all). ([#191](https://github.com/GenvidTechnologies/construct3-chef/issues/191))

### 0.8.0

**mcp-utils 0.8.0** (`^0.7.0`→`^0.8.0`) shipped the three capabilities ADR [`0029`](../decisions/0029-flat-docs-alias-generated-into-the-tarball.md) named explicitly as its retirement condition, closing [mcp-utils#15](https://github.com/GenvidTechnologies/mcp-utils/issues/15): `exposeDocs` gained an optional `docsDir` option (default `"docs"`, preserving pre-0.8.0 behaviour), an optional `recursive` option (default `false`, likewise preserving it), and a real `list` callback — where every prior version registered its templated resource with `list: undefined`, leaving it absent from `resources/list`. The resource template itself changed shape, `docs:///{name}` → `docs:///{+path}` (RFC 6570 reserved expansion), so a nested name now resolves; a flat name still resolves identically, since reserved expansion matches a no-separator name too. A **real bump, not adoption-only** — `^0.7.0` resolves to `>=0.7.0 <0.8.0-0`, so the range excluded 0.8.0 and the lockfile was pinned at 0.7.0 until this bump, the same shape the 0.6.0 and 0.7.0 entries above already establish for this package. Both option defaults preserve prior behaviour, so the bump alone (before any call-site change) was inert — the suite held at its exact pre-bump baseline.

Chef adopted the shipped capabilities in [#207](https://github.com/GenvidTechnologies/construct3-chef/issues/207): `server.ts`'s `exposeDocs(server, __pkgDir, { docsDir: "wiki", recursive: true })` now points the docs resource directly at the wiki tier, serving every tracked page at its real path (`docs:///reference/cli`), enumerable, with no packaging step. `package.json`'s `files` already carried `"wiki"` from ADR 0028's consolidation, so this required no packaging change of its own — only deletion: `scripts/gen-docs-alias.mjs`, `test/wiki/docsAlias.test.ts`, the `docs:alias` npm script, the `prepack` `docs:alias` step, and the whole `postpack` entry are all gone, and `"docs"` is dropped from `files`. See ADR [`0033`](../decisions/0033-mcp-docs-resource-serves-wiki-directly.md) for the full adoption record, including why ADR 0029's dev/installed asymmetry no longer exists and why [#200](https://github.com/GenvidTechnologies/construct3-chef/issues/200)'s repath objection to a local, enumerable `exposeDocs` no longer holds now that upstream shipped the same capability.

**Revert-confirm (per `CLAUDE.md` § "Leaf dependencies"), applied in its degenerate form.** The rule asks: for each local guard the upstream change overlaps, delete it and confirm a test still fails. Here there was nothing left to selectively delete and re-test — the entire local flattener (`gen-docs-alias.mjs`, its `--check` oracle, and `docsAlias.test.ts`) *was* the guard the upstream behaviour now overlaps, and it was deleted wholesale as part of the adoption itself rather than left in place to be checked for staleness after the fact. The obligation the rule protects against — a local clause silently converting from guarded to unguarded with no diff and no failing test to notice — cannot arise here, because there is no local clause left to go quietly vacuous; `test/mcp/docsResource.test.ts` was rewritten against the new served surface (committed deliberately red before the adoption landed, per this repo's standing guard-work discipline) rather than left asserting against the old flattened one.

**Next-bump check.** None outstanding — the retirement condition this section closes was mcp-utils#15's only open ask against `exposeDocs` for chef's use.

### Follow-up filed at 0.8.0 — `resolveRootFolder`'s discarded `matches[]`

[#95](https://github.com/GenvidTechnologies/construct3-chef/issues/95) (multi-project MCP support, ADR [`0034`](../decisions/0034-mcp-server-multi-project-support.md)) needed the set of candidate roots `resolveRootFolder` finds during ambiguous discovery (≥ 2 immediate child directories each containing `project.c3proj`), to seed a future auto-discovered multi-root registry. `resolveRootFolder` already computes that full candidate set internally — it has to, to know discovery is ambiguous — but surfaces it only as prose interpolated into the `mcpError` string it returns, with no structured field carrying the list.

**Declined: scraping the error string with a regex to recover the candidate list.** This would be the first place in this repo treating an error message as structured data. Upstream may reword the message at any patch release with no version signal a consumer could act on, and a regex that stops matching degrades **silently** to an empty registry rather than a visible failure — exactly the failure shape this repo's own conventions warn against elsewhere (a check that fails quietly is worse than one that fails loudly). See ADR 0034 decline 6.

**Filed instead, now, rather than waiting for the gap to recur:** [`GenvidTechnologies/mcp-utils#20`](https://github.com/GenvidTechnologies/mcp-utils/issues/20) asks `resolveRootFolder` to return its already-computed candidates as structure — either an additional `matches?: string[]` field on the ambiguous-discovery error result, or a plural `resolveRootFolders` that returns every match directly. **Gates nothing in chef today** — #95 shipped v1 with explicit multi-root config only (repeated `--project-dir` / `C3_PROJECT_DIRS`), and multi-root auto-discovery stays deferred to v2 regardless of when this ships (ADR 0034 decline 7). Recorded here, not in CLAUDE.md, because it is scoped to a specific upstream version gap rather than a posture that survives every release.

**Next-bump check.** When `@genvidtech/mcp-utils` next ships, check whether mcp-utils#20 landed; if so, evaluate whether v2's multi-root auto-discovery should adopt it rather than deriving ids from a hand-rolled re-implementation of the same discovery walk.

### 0.9.0

**mcp-utils 0.9.0** (`^0.8.0`→`^0.9.0`) is the answer to the 0.8.0 follow-up above: [`GenvidTechnologies/mcp-utils#20`](https://github.com/GenvidTechnologies/mcp-utils/issues/20) landed, but not in the shape asked for. The request offered two options — an additional `matches?: string[]` field on the ambiguous-discovery error, or a plural collector. Upstream shipped the **plural**: `resolveRootFolders(opts, env?, readdir?)`, returning `{ paths: string[]; source }`, where two-or-more matches is now a **success** carrying every candidate rather than an error at all. Upstream's own ADR-0006 records the reasoning, and it is decline 7's framing turned around: for the caller that wants the candidate list, ambiguity is the *input*, not a failure, so putting candidates on an error result would force that caller to reach a success through `isMcpError`. `resolveRootFolder` (singular) is now reimplemented as a thin wrapper over `resolveRootFolders`, and its ambiguous-branch `mcpError` message is **byte-identical** to 0.8.0's.

A **real bump, not adoption-only** — `^0.8.0` resolves to `>=0.8.0 <0.9.0-0`, so the range excluded 0.9.0 and the lockfile was pinned at 0.8.0 until this bump, the same shape every prior mcp-utils entry in this section establishes. The bump itself is **inert for chef today**: the full `dist/` diff is a `walkFiles` docstring path fix (`docs/decisions/` → `wiki/decisions/`, pointing at *upstream's own* decision record for that function — mcp-utils reorganized its documentation the same way chef did at ADR 0028, but independently of it), the `resolveRootFolder`→wrapper reimplementation above, and two purely additive `index.d.ts` export lines (`resolveRootFolders`, `txToken`).

**Decline 7's second blocker is now also cleared, by a different route.** Decline 7 named two blockers to multi-root auto-discovery: no structured candidate list (cleared by `resolveRootFolders` above) and "discovery produces bare paths, with no id-derivation step built in." That second blocker was cleared not by this bump but by #212 itself, which built `deriveProjectId(root, usedIds)` in `src/mcp/projectRegistry.ts` (sanitized basename, `-2`/`-3` dedup, stderr warning on collision) to derive ids for the explicit multi-root config it shipped. Both blockers are cleared; auto-discovery adopting `resolveRootFolders` for ADR 0034 decline 7's deferred v2 is now unblocked, and is filed as [#216](https://github.com/GenvidTechnologies/construct3-chef/issues/216) — which also carries the ADR 0034 decline 7 amendment.

**Declined — `txToken` codec, not adopted in this bump.** 0.9.0 also ships a `txToken` module whose own docstring names `GenvidTechnologies/construct3-chef` as one of two intended consumers (the other being `c3-domain-manager`), citing its own `wiki/decisions/0005-tx-token-wire-format.md`. It overlaps `src/mcp/txToken.ts`, which #212 shipped days earlier — and the semantics diverge materially enough that swapping them is not a mechanical adoption:

| | chef `src/mcp/txToken.ts` | mcp-utils 0.9.0 `txToken` |
|---|---|---|
| `formatTxToken` on a bad id/n | returns a formatted string regardless | **throws `TypeError`** |
| `parseTxToken` failure | `{error: string}` | **`null`** |
| split point | **last** `:` | **first** `:` |
| counter with leading zeros (`"05"`) | accepted | **rejected** |
| whitespace-bearing ids | accepted | **rejected** |
| `compareTxToken` | `(ctx, token, action)` → `CallToolResult \| null` | `(token, projectId, currentN)` → `boolean` |

Two reasons, not one: (a) the semantics genuinely diverge (table above) against an existing 162-line `test/mcp/txToken.test.ts` chef would need to reconcile line by line; (b) per CLAUDE.md's adoption posture, chef's `compareTxToken` is **rendering/policy** — it builds `mcpError` with per-site action verbs (`applying`/`syncing`/`scaffolding`) and a `txId:` footer — which stays local regardless of what upstream owns. The *codec* half (format/parse/validate) is a legitimate upstream candidate on its own; the *comparison* half is not. Deferred to [#217](https://github.com/GenvidTechnologies/construct3-chef/issues/217) rather than folded into this bump, with the divergence table above and the existing test suite as the reconciliation surface.

**Next-bump check.** When `@genvidtech/mcp-utils` next ships, check whether [mcp-utils#25](https://github.com/GenvidTechnologies/mcp-utils/issues/25) landed — it asks `parseTxToken` to surface *why* a parse failed instead of returning a bare `null`, and it is the specific gate on adopting the codec ([#217](https://github.com/GenvidTechnologies/construct3-chef/issues/217) tracks the adoption decision). chef's parser produces three distinct diagnostic templates that `compareTxToken` renders straight to the client (missing separator, empty project id, non-integer counter); upstream currently collapses all three to `null`, and re-deriving that classification locally is the drift trap this posture exists to avoid. Also check whether a later release narrows the other semantic gaps in the table above (in particular, whether `formatTxToken`/`parseTxToken`'s throw-vs-error-value and split-direction choices are reconsidered) before re-evaluating the swap. **Partially resolved 2026-09-02:** the *id-validation* half shipped without waiting on upstream — `ProjectRegistry.add` now guards with upstream's `isValidProjectId` (ADR [`0036`](../decisions/0036-project-id-guard-uses-the-upstream-wire-format-rule.md)), because chef was minting ids that upstream's parser rejects, making a chef-minted token unparseable by this format's other named consumer. That was an interop defect independent of the codec decision. The codec swap itself remains declined pending mcp-utils#25.
